# 协作交接：从静态候选转到真实验证

## 当前优先级

伙伴反馈强调静态能力已经较齐，下一阶段要用真实运行证据完成案例，而不是
继续用分析器数量、单测数量替代比赛成果。W3“至少一个带运行证据的漏洞”
作为团队里程碑保留，不把它当成已完成成果或主办方给定的数量要求。

本轮避开另一个正在修改的组件流水线工作会话，独立新增 `runtime_evidence`
与对应测试。复用已有结果、报告校验及源码快照；不另建扫描器、不改变合成
harness的含义、不代填真实执行授权。合作伙伴正在做的集成变更另行验收。

## 必须由项目负责人确定的三个事项

| 事项 | 请确认的最小信息 | 自动工程的边界 |
| --- | --- | --- |
| 产品与版本矩阵 | 首批运行验证的产品/模块、固定版本或manifest、真实构建配置和工具链位置 | 可先批准一个可运行配置作为首个案例，不削减最终组件/漏洞族目标；既有宿主profile不能冒充产品构建 |
| 隔离环境与执行授权 | VM/容器/模拟器/专用设备、镜像标识、可恢复方式、允许执行的目标和操作、资源限制、授权责任人 | 源码访问权限、聊天中的“继续项目”、JSON里一个approved字段，都不由工具自动变成真实目标执行授权 |
| 复核与提交责任人 | 安全影响/重复性复核人及最终私下提交人，可由你和伙伴分担 | 工具不以状态机或模型文字代替最终审核，不自动提交漏洞 |

建议把首个运行环境设为可销毁且可复位、无生产数据、目标源码只读挂载的
专用环境；具体CPU/内存/时限由环境负责人确认。以上是方案建议，不是已经
获得的授权。LLM继续暂缓，无需为本轮提供凭据。

## 接下来按案例推进，不继续无限扩展静态功能

1. **候选准入。** 从已经绑定证据的候选里，先说明违反的安全边界、输入控制
   和适用配置。普通API提示或死存储不会直接进入“已确认漏洞”列表。
2. **构建与原版复现。** 在确认的隔离范围内固定PoC、源码和构建配置，保留
   失败和成功运行记录。构建失败不是未触发，单次崩溃不等于安全漏洞。
3. **独立复现与修复。** 独立任务/重置后的会话复现，再做修复版及正常功能
   对照。补丁“不再崩溃”不能替代路径覆盖、根因消除和功能回归检查。
4. **报告和人工审核。** 复用现有候选报告，导入运行证据附录，再补真实分支
   影响、修复依据和复核结论。未确认项明确保留，不能用合成数据填满交付件。

接收接口及命令见 `docs/engineering/RUNTIME_EVIDENCE.md`。本轮真实源码仅用于
准备候选交接，并不执行目标。运行记录缺失时，W3仍未完成；授权就绪也不保证
立即发现新漏洞，还必须完成安全影响和可复现性的实际验证。

## 并行开发约定

本轮文件域：`ohvul/runtime_evidence.py`、`tests/test_runtime_evidence.py`、本交接
说明和运行证据使用说明。已有流水线、分析器、复核队列及HUMAN_ACTIONS变更
归另一个工作会话，未抢占或回滚。共享目录的长验收串行运行；后续并行编码
优先使用独立工作树/PR，避免两边反复使对方的源码快照失效。
