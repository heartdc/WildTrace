摘要
摘
要
随着移动互联网技术的快速迭代和智能终端设备的普及，用户对移动应用的依
赖不断加深，针对移动应用的攻击也逐渐增多，移动应用的安全性问题变得尤为突
出。随着HarmonyOS NEXT 操作系统的问世，基于该操作系统开发的原生应用将迎
来爆发式增长。鸿蒙应用使用华为公司自主研发升级的ArkTS 语言进行开发，不像
Android 和iOS 应用已经形成了相对成熟的应用安全防护体系并积累了丰富的安全分
析方法和工具链，鸿蒙ArkTS 应用的安全分析方法与工具严重匮乏。因此，针对鸿
蒙ArkTS 应用的安全分析工具的研究与开发，是确保HarmonyOS 生态健康发展的重
要因素。
针对上述问题，本研究旨在通过对ArkTS 语言构建静态污点分析引擎对鸿蒙移
动应用进行代码安全分析，通过基于指针分析的污点分析算法实现了针对ArkTS 的
代码安全分析，具体贡献如下：
（1）构建静态污点分析引擎并构建评估数据集。本研究基于ArkAnalyzer 项目提
取的中间表示进行高层分析任务的研究，首次实现了ArkTS 全程序指针分析以及污
点分析框架。框架主要包含指针分析、污点分析和插件系统三部分，通过Andersen 指
针分析算法实现变量级数据流跟踪并通过污点分析插件处理污点流动以检测污点流，
并引入插件系统赋予框架优秀的可扩展性。同时，借鉴xAST 数据集构建了评估分析
工具分析能力的ArkTS 数据集。该数据集聚焦于ArkTS 语言的各种代码场景，如数
据类型、表达式、函数调用等方面，共计226 个案例，旨在评估分析引擎在各种代码
场景下的分析能力。在自建的数据集上对本研究的分析引擎进行了评估，评估结果较
为乐观，召回率达到77.9%。
（2）结合大语言模型优化污点分析。为了可以将大语言模型的代码理解能力作用
于静态代码分析中，本研究设计了一种结合大语言模型的污点转移自生成策略。该策
略利用大模型的代码理解能力，针对库函数自动生成其污点传播方向，此方法可以使
得污点分析更加自动化且智能化。实验结果表明本方法可以有效地针对库函数生成
其污点转移规则，避免污点中断，可以更好地找到存在的污点流。并且针对不同大语
言模型进行了准确率、分析时间、费用上的对比，最终发现DeepSeek-Chat 模型在该
场景下的表现最为出色。
在鸿蒙移动ArkTS 应用代码安全分析领域，本研究借助已有工作ArkAnalyzer，
从无到有地实现了首个ArkTS 污点分析框架，可以对ArkTS 应用进行更高层次的代
码安全分析，并且通过插件系统使得该框架具有更高的拓展性，同时借助大语言模型
进一步增加了分析引擎的自动化以及智能化。分析框架在自建数据集上的评估结果

ABSTRACT
ABSTRACT
With the rapid evolution of mobile Internet and smart devices, mobile app security has be-
come critical due to growing usage and increasing attacks.The introduction of HarmonyOS
NEXT is expected to drive rapid growth in native application development for this plat-
form.HarmonyOS applications are developed using ArkTS, a proprietary language enhanced
by Huawei. Unlike Android and iOS, which have established mature security protection sys-
tems and accumulated rich analysis methods and toolchains, security analysis methods and
tools for HarmonyOS ArkTS applications are severely lacking.Therefore, the research and
development of security analysis tools for HarmonyOS ArkTS applications is crucial for en-
suring the healthy development of the HarmonyOS ecosystem.
To address the above issues, this study aims to perform code security analysis on HarmonyOS
mobile applications by constructing a static taint analysis engine for the ArkTS language.
Through a pointer-analysis-based taint analysis algorithm, we achieve code security analysis
tailored for ArkTS. The specific contributions are as follows:
（1）Construction of a static taint analysis engine and evaluation dataset. Based on the in-
termediate representation extracted by ArkAnalyzer, this study conducts high-level analysis
tasks and implements the first whole-program pointer analysis and taint analysis framework
for ArkTS. The framework consists of three main components: pointer analysis, taint analy-
sis, and a plugin system. It employs the Andersen pointer analysis algorithm to track variable-
level data flow and uses taint analysis plugins to handle taint propagation for detecting taint
flows, while incorporating a plugin system to provide excellent extensibility. At the same
time, inspired by the xAST dataset, this study constructs an ArkTS evaluation dataset for
assessing analysis tool capabilities. The dataset focuses on various ArkTS code scenarios,
such as data types, expressions, and function calls. It comprises 226 cases and is designed
to evaluate the analysis engine’s performance across different code scenarios. Evaluation on
this self-constructed dataset shows promising results, with a recall rate of 77.9%.
（2）Optimization of taint analysis integrated with large language models. To use the code
understanding capabilities of LLMs for static code analysis, this study designs a strategy
for automatic generation of taint transfer rules using LLMs. This strategy utilizes the code

西安电子科技大学硕士学位论文
understanding ability of large models to automatically generate taint propagation directions
for library functions, enhancing automation and intelligence in taint analysis. Experimen-
tal results demonstrate that this method can effectively generate taint transfer rules for li-
brary functions, avoid taint propagation interruptions, and better identify existing taint flows.
Furthermore, evaluation of different LLMs on accuracy, analysis time, and cost shows that
DeepSeek-Chat performs best in this scenario.
In the field of code security analysis for HarmonyOS ArkTS applications, this study builds
upon the existing ArkAnalyzer to implement the first ArkTS taint analysis framework, en-
abling higher-level code security analysis for ArkTS applications.The plugin system provides
the framework with enhanced extensibility, while the integration of LLMs further increases
automation and intelligence. The analysis framework achieves promising results on the self-
constructed dataset, with a recall rate of 77.9%, representing improvements of 14.3% and
25.4% over baseline methods. This framework provides a solution for code security analy-
sis of ArkTS applications and contributes to the mobile application security field within the
HarmonyOS ecosystem.

1.1 研究背景与研究意义
在数字化转型加速推进的今天，智能终端设备已深度融入人类社会的各个领域，
其中智能手机更是成为连接个人数字生活的核心入口。移动应用作为智能手机功能
实现的载体，不仅承载着用户的日常工作、社交、娱乐等多维度需求，还在数字支付、
身份认证、信息传输等关键场景中扮演着不可替代的角色。随着移动应用使用深度和
广度的持续提升，其所面临的安全威胁也呈现出多样化、复杂化的特点。因此，构建
系统化、精细化的移动应用安全分析体系，不仅关系到用户个人信息安全和数字资产
保护，更是维护整个移动互联网生态健康发展的重要基础。
华为公司一直致力于研发自主生态，2024 年10 月，华为推出“纯血鸿蒙”Har-
monyOS NEXT，彻底剥离Android 兼容层，从内核到应用生态全面自主化。该操作
系统不再支持Android 应用，转而支持经过其改进过的ArkTS 语言开发的应用。这
一重大举措使得移动操作系统发生很大改变。在此之前，全球移动操作系统几乎只
有Android 以及iOS，而像Xiaomi HyperOS、OPPO ColorOS 等操作系统严格来说是
Android 操作系统，只是进行了一些本土化优化和创新。而HarmonyOS NEXT 的到来
完全改变了这种格局，可以说是全球第三大移动操作系统。
近年来，华为移动终端的国内市场份额一直保持在前列，在HarmonyOS NEXT
出现后，更是进一步提高了其销售量。如图1.1所示，根据Counterpoint[1]提供的数据，
华为智能手机在2025 年第二季度在国内智能手机市场份额中以18.1% 占据榜首，对
比2024 第二季度的15.0% 增长17.6%。目前HarmonyOS 已经成为国内第二大移动操
作系统。
随着智能终端销量的不断提升，鸿蒙自主生态也在迅速发展。截至2025 年1 月，
鸿蒙系统生态设备已突破10 亿台，注册开发者达675 万，覆盖手机、汽车、家电等
全场景终端。除了硬件设备突破之外，鸿蒙生态应用呈现持续增长态势。从APP 数
量来看，目前原生鸿蒙APP 已超过2 万，覆盖了用户95% 以上的使用时间，也就是

1.3.1 静态程序分析
基于静态分析技术的代码安全检测系统一般包含三个核心组成部分：程序表示
层、检测规则库和分析执行引擎。程序表示层负责将源代码转换为适合机器处理的
结构化形式，常用的表示方法包括抽象语法树、控制流图以及数据流图等。检测规则
库存储了各类安全缺陷的识别模式，这些模式通常来源于对历史漏洞案例的总结或
安全编码标准的规范定义。分析执行引擎则是整个系统的驱动核心，它负责在程序表
示上应用检测规则，通过模式匹配、数据流追踪等技术手段来发现可能存在的安全漏
洞。该过程主要依赖于控制流分析、数据流分析、污点分析等经典算法的支撑。

学术界和工业界在静态分析领域开展了大量研究工作，涌现出众多各具特色的
检测工具。在早期研究中，Kim 等人在2008 年开发了一款漏洞检测系统[2]，该系统
接受源代码和漏洞模式规则作为输入，能够定位出符合特定漏洞特征的代码片段及
其执行路径。除了直接处理源代码外，将程序转换为图结构再进行分析也是主流技术
路线之一。例如，Tabby 工具[3]采用代码属性图作为程序表示，并借助图数据库技术
来挖掘Java 程序中潜在的反序列化攻击链。符号执行作为另一重要技术分支，同样
在漏洞检测中发挥着关键作用。Trinh 等人于2014 年推出的符号字符串求解器S3[4]，
便是专门面向Web 应用安全漏洞检测的符号执行工具。
针对传统静态分析技术存在的误报率高、处理复杂代码能力不足等问题，部分
研究者开始探索动静结合的分析方法。Distefano 等人在2014 年提出了一种混合分析
方案[5]，其核心思想是将动态执行过程中收集的具体行为抽象成动态约束，然后将这
些约束作为补充信息融入静态分析流程，从而提升分析精度。交互式应用安全测试
（IAST）技术[6]则通过在目标程序中插入探针代码，实时采集程序运行时的控制流和
数据流信息，并综合运用静态和动态两种分析手段进行漏洞判定，有效降低了漏报和
误报率。
静态分析技术虽然能够实现无需实际执行程序即可进行全代码覆盖的安全检查，
但在实际应用中也面临着诸多挑战。首先，误报问题一直是困扰静态分析的主要难
题，由于静态分析通常采用保守的近似策略，容易将正常代码误判为存在漏洞，导致
大量需要人工复核的虚假警报，增加了安全审计的工作负担。其次，静态分析对新型
未知漏洞的发现能力有限，因为其检测逻辑依赖于预先定义的规则或模式，难以应对
从未见过的新型攻击手法。最后，当面对包含复杂指针操作、多态调用等特性的代码
时，静态分析的精度往往会显著下降，难以给出可靠的判断结果。
1.3.2 机器学习与深度学习

向量，然后利用训练好的分类模型来判断代码是否存在安全漏洞。与基于预定义规则

代码特征，并训练多个概率分类模型来识别SQL 注入和跨站脚本漏洞；Sonnekalb 等

大语言模型直接应用于代码漏洞检测。一些研究工作[25]尝试将源代码直接作为
输入提供给LLM，借助模型的文本分类或文本生成能力来识别代码中的安全缺陷。

2.1 静态程序分析技术
静态程序分析（Static Program Analysis）是一种在不实际执行程序的前提下，通
过分析其源代码、字节码或中间表示来推理程序行为和属性的关键技术。它通过抽象
解释、数据流分析、类型推导等理论方法，构建程序模型并对其进行系统性地遍历和
检查，旨在发现潜在的运行时错误、安全漏洞，并验证程序是否满足特定的规约或安
全策略。其核心优势在于能够实现全路径、全输入的覆盖性检查，广泛应用于编译器
优化、代码质量保障、安全审计和形式化验证等领域。
2.1.1 基础理论
抽象解释（Abstract Interpretation）是由Patrick 和Radhia Cousot 于1970 年代提
出的、用于静态程序分析的理论框架。其核心思想是：为了在有限时间和资源内分析
程序的潜在行为，需要对程序的实际语义进行简化。它通过定义一个比程序“具体语
义”更简单、更粗糙的“抽象域”（例如，用符号正、负、零来抽象所有整数），并
设计对应的“抽象操作”来模拟程序步骤。分析过程会计算出一个在抽象域上的、包
含所有可能具体行为的“近似结果”。这种近似必然会导致精度损失，但其关键优势
在于保证了分析的可靠性与可终止性——如果抽象分析说“某处不会有运行时错误”，
那么具体运行时也一定不会有。因此，抽象解释为构建可靠且实用的静态分析器奠定
了坚实的数学基础。如今较为流行的分析方法都离不开抽象解释，后续本研究中涉及
的指针分析、污点分析等技术都可以看作是抽象解释在特定领域的应用实例。

的后续程序点加入工作表，直到工作表为空，此时算法收敛并得到最终解。该算法的
关键优势在于它避免了每次迭代都遍历所有程序点的开销，而只聚焦于值实际发生
变化的区域，从而在求解诸如到达定值、活跃变量、常量传播等问题时，相比朴素的
迭代算法能实现显著更高的效率，成为现代编译器优化和静态分析工具中数据流求
解器的标准实现方法。后续研究中涉及的指针分析便是采用工作表算法框架实现的。

污点分析（Taint Analysis）。污点分析是一种用于追踪程序中特定敏感数据（称

在安全漏洞，如SQL 注入、跨站脚本、命令注入或信息泄露。污点分析是实现数据
流安全策略和自动化漏洞挖掘的关键技术，广泛应用于安全审计工具、漏洞检测系统

智能体（Agent）[56-57]是具备感知、规划、工具调用和自主执行能力的AI 单元，能

合能构建强大的智能系统：工作流作为“骨架”负责流程编排与调度，而Agent 作为

3.1 指针分析实现
Arktan 的指针分析算法是借鉴Andersen 指针分析算法框架[59]实现的。Andersen
指针分析算法是一种经典的、流不敏感的基于子集约束的指针分析算法。它将程序中
的指针赋值（如p = q）系统地转换为子集约束（如“q 的指向集是p 的指向集的子
集”），并通过求解这些约束的闭包，计算出每个指针所有可能指向的抽象内存位置。
以下将从入口方法处理、算法核心实现、特性适配等方面详细介绍本研究设计实
现的针对ArkTS 语言的指针分析算法。
3.1.1 入口方法处理
对于一个全程序指针分析，入口方法的处理至关重要，因为一旦处理不当，分析
将无法覆盖整个程序，造成分析精度下降。Java、C 等语言开发的项目大多都会拥有
一个Main 方法作为整个项目的入口，在分析这些项目时，只需要将Main 方法作为分
析的入口方法便可以进行全程序分析。但是ArkTS 语言面向的是移动应用开发，并
没有Main 方法来作为项目的入口，因此处理ArkTS 项目的入口方法便是针对ArkTS
应用进行全程序指针分析的关键。
本研究借鉴了针对安卓应用的全程序分析对于入口方法的处理，希望构造一个
DummyMain 方法来作为分析的入口，而这个DummyMain 方法则是由应用组件的各
个生命周期方法组成。在使用ArkAnalyzer 时，发现其实现了DummyMainCreater 类
用以进行DummyMain 方法的构造，其原理便是收集各个生命周期方法，都作为语句
共同组成一个DummyMain 方法，如图3.2。

与其他自定义页面进行通信。因此正确分析主页面build 方法是关键。
而在实验过程中发现，ArkAnalyzer 在构造DummyMain 方法时，仅仅将各个生

3.1.3 特性适配
ArkTS 作为编程语言也会有其一些独特的语言特性，那么为了提高分析精确度，
本研究对其某些语言特性进行了相应的适配工作。
特殊的数据类型。ArkTS 的数据类型除了有比较经典的数据类型，如整型、浮点
型、字符串等等，还有其独有的特殊数据类型——FunctionType，如图3.3，可以将一
个方法赋值给一个变量，然后通过该变量来进行此函数的调用，这是一个很有趣的
语言特性。除此之外，其箭头函数、闭包、lambda 表达式也会有类似的结构，将一
个函数体赋值给一个变量，然后变量进行调用。对此，本研究对指针分析算法进行了
修改以支持这种特性。ArkAnalyzer 已经为FunctionType 进行了建模，并且可以通过
FunctionType 拿到其对应的具体函数，因此解决此语法特性的关键在于将变量与对应
的变量函数建立联系，如此在处理函数类型的变量时，可以通过这种联系找到对应的
函数调用语句并且进行函数的具体解析，达到分析变量函数的目的。本研究通过一个
全局list 来记录分析过程中无法解析的函数，然后在处理指针传播时，遍历这个list，
寻找与当前指针姓名相同的函数，找到之后，将其两者进行关联，并在之后进行相关
处理。通过这种算法的设计，本研究实现了对函数变量、箭头函数、闭包、lambda 表

3.3 污点分析实现
污点分析是一项重要的程序分析技术，其主要通过追踪数据流来观察敏感信息
（污点数据）在程序运行中的传播过程。广泛应用于漏洞检测、恶意代码分析、隐私
保护等领域。
上文提到过，由于污点分析与指针分析的契合度非常高，因此基于指针分析来实
现污点分析会很便捷。因此，本研究基于上述实现的指针分析，完成了针对ArkTS 语
言的污点分析设计，可以通过追踪数据流来观察ArkTS 代码中敏感信息的传播过程。
污点分析中三个重要元素为source、transfer、sink，其中source 代表污点源，即
认为存在安全风险的变量，如外部输入变量；sink 代表污点汇聚点，即存在安全风险
的方法，如果有污点数据流到了sink 点，便认为该程序存在安全风险，如图3.8。比
较典型的sink 有执行sql 语句的方法、命令执行的方法等；transfer 表示要帮忙进行污
点传播的方法，尽管目前的程序分析技术可以实现较为精确的过程间分析，但是编程
语言的内置类方法（如string 类的方法）并不建议进行分析，因为这些内置类方法底
层往往会调用其他的内置类方法，可能调用链极其复杂，目前的程序分析技术在处理
这种极其复杂的调用方法时可能会出现意料之外的错误。但是大部分内置类方法都
会有数据的流动（如string 类的concat 方法），那么这些方法就需要通过设置transfer
来保证污点的正确传播。

第四章

本章针对传统静态污点分析中库方法导致的污点传播中断问题，提出了一种结

基于上述提到的污点中断问题，在当前的污点分析研究中有两种解决方案：
（1）不限制分析引擎的Method 分析限制，使其可以自动分析库方法。如今的静
态分析引擎大部分都可以进行跨过程分析，即可以分析Method，包括参数传递以及
接收返回值，基本可以确保跨过程数据流分析的正确性。依靠这一技术，可以让分析
引擎自动分析库方法，即进入库方法的内部。采用这一方法有一定概率可以解决上述
提到的污点中断问题，但是却会引入更多的问题。由于库方法内部还要调用其他库方
法，导致库方法的调用栈往往会非常深，因此表面上在分析一个库方法，实际上可能
需要分析成几十甚至上百个库方法，这不仅会导致分析效率降低，而且由于上下文的
问题还会引入大量的误报。因此很少会使用这种方法来解决库方法污点中断问题。
（2）人工配置transfer，帮助分析引擎传递污点。这是目前大多数污点分析引擎
都在采用的方法，创建一个污点配置文件，在该文件中配置相应库方法的transfer，利
用这个transfer 来辅助分析引擎进行库方法的污点转移。这一方法虽然比较便捷准确，
但是需要依靠人工的经验，研究人员甚至需要提前在待分析的代码中找到污点流以
及污点流中可能涉及的库方法，然后再在配置文件中为这些库方法配置transfer。在
我看来，这种方法违背了自动化分析的初衷，可能也会造成准确性的下降。
结合上述两种方法的优缺点，本研究提出了一种结合LLM 进行污点转移自生成
的方法，通过利用LLM 的代码理解能力，思考库方法的污点转移方法，自动生成其
污点转移规则，然后指导分析引擎进行污点转移。该方法不仅能节省人工，增强污点
分析的自动化程度，也能一定程度上提升分析精度。
4.1 智能污点转移插件
智能污点转移插件是在第三章中的污点转移插件的基础上进行扩展和增强的，其
核心思想是将传统的人工配置污点转移规则的方式转变为利用LLM 自动生成规则的
方式。如附录B.1 所示，该插件通过监听指针分析过程中的CallEdge 事件，实时捕获
库方法调用，并借助LLM 的代码理解能力自动推断污点转移规则。
4.1.1 插件架构设计
智能污点转移插件采用事件驱动架构，主要由四个核心模块组成：（1）事件监听
模块：通过实现指针分析框架的onNewCallEdge 接口，实时监听分析过程中产生的函
数调用边；（2）方法识别模块：判断被调用方法是否属于库方法，通过检查方法的声
明位置（如是否位于系统库或第三方库中）进行区分；（3）LLM 交互模块：负责构
造HTTP 请求，将方法签名发送给Dify 服务器，并处理返回的污点转移规则；（4）规
则应用模块：解析LLM 返回的JSON 格式规则，并将其转换为指针分析框架内部的
污点转移操作。

4.1.2 工作流程
智能污点转移插件的工作流程可以分为五个阶段。第一阶段，插件在指针分析
初始化时注册到分析框架中，通过onNewCallEdge 接口建立对CallEdge 事件的监听。
第二阶段，当指针分析遇到新的函数调用语句时，触发onNewCallEdge 回调，插件获
取被调用方法的签名信息（包括方法名、参数类型、返回值类型等）。第三阶段，方法
识别模块判断该方法是否属于库方法，若是库方法且未在配置文件中预定义transfer
规则，则进入LLM 交互阶段。第四阶段，LLM 交互模块构造包含方法签名的HTTP
POST 请求，发送给Dify 服务器的工作流接口，并同步等待响应结果。第五阶段，规
则应用模块解析LLM 返回的JSON 格式污点转移规则，根据规则中的from 和to 字
段在指针流图上添加相应的边，实现污点数据的正确传播。
4.1.3 与传统插件的对比
与第三章中的传统污点转移插件相比，智能污点转移插件具有显著优势。传统插
件完全依赖人工在配置文件中预定义transfer 规则，对于未配置的库方法会直接忽略，
导致污点传播中断。而智能插件能够动态处理任意库方法，无需人工预先配置，大大
提升了分析的自动化程度。此外，传统插件的规则质量完全依赖于研究人员的经验和
领域知识，容易出现遗漏或错误；智能插件利用LLM 强大的代码理解能力，能够生
成更准确、更全面的污点转移规则。在可扩展性方面，智能插件通过LLM 的泛化能
力，可以处理未见过的库方法，而传统插件需要为每个新方法手动添加规则。
4.2 基于大语言模型的污点转移规则生成
该模块是整个智能污点转移系统的核心，负责利用LLM 的代码理解能力自动推
断库方法的污点转移规则。该模块在接收到分析插件传入的方法签名后，首先利用
LLM 进行污点转移分析，判断当前方法是否满足污点传播条件以及具体的传播路径。
4.2.1 提示词工程设计
提示词工程是确保LLM 生成高质量污点转移规则的关键。本模块的提示词设计
采用结构化提示策略，包含以下关键组成部分：（1）角色定义：将LLM 设定为” 静态
程序分析专家”，明确其任务是分析代码并生成污点转移规则；（2）任务说明：清晰
描述污点分析的目标和意义，帮助LLM 理解上下文；（3）污点转移条件说明：明确
定义允许进行污点转移的各种场景，包括参数到返回值的传播、参数间的相互传播、
对象字段与参数间的传播等；（4）规则格式规范：详细说明输出规则的结构，包括
from、to、type 等字段的含义和取值范围；（5）规则示例展示：采用少样本提示技术，
提供3-5 个典型的污点转移规则示例，帮助LLM 理解期望的输出格式；（6）输出格

式要求：强制要求输出必须采用JSON 格式，并规定必须包含的字段和可选字段，确

4.2.2 规则生成与验证
规则生成过程分为三个阶段。第一阶段，LLM 接收方法签名和提示词，进行推理
分析，生成初步的污点转移规则。第二阶段，代码执行节点对LLM 输出进行解析和
验证，检查JSON 格式的正确性、字段完整性、取值合理性等。第三阶段，对于验证
通过的规则，返回给分析引擎应用；对于验证失败的规则，记录错误信息并返回默认
规则（如不进行污点传播）。这种多层次的验证机制确保了系统的鲁棒性，即使LLM
输出异常也不会导致分析引擎崩溃。
4.2.3 规则缓存机制
为提高分析效率，避免重复调用LLM，本模块实现了规则缓存机制。当首次分
析某个库方法时，调用LLM 生成规则并将结果缓存到本地文件中，缓存的键为方法
签名的哈希值，值为生成的污点转移规则。后续遇到相同方法时，直接从缓存中读取
规则，无需再次请求LLM。缓存机制显著降低了LLM 调用次数，提升了整体分析性
能。实验表明，对于典型的ArkTS 应用，缓存命中率可达80% 以上，有效减少了分
析时间和API 调用成本。

4.3.1 工作流架构
Dify 工作流采用线性流水线架构，包含三个主要节点：（1）开始节点：接收来自
分析引擎的HTTP 请求，提取方法签名等输入参数，并将其传递给后续节点；（2）知
识检索节点：基于ArkTS 的API 文档构建知识库，使用向量检索技术查找与方法签
名相关的文档片段，为LLM 提供准确的上下文信息；（3）LLM 节点：结合提示词、
知识库检索结果和方法签名，进行推理分析，生成污点转移规则；（4）代码执行节点：
处理LLM 的输出结果，提取其中的JSON 数据，进行格式验证和错误处理，最终返
回标准化的响应给分析引擎。这种模块化设计使得工作流易于维护和扩展，各节点职
责清晰，便于调试和优化。

4.3.2 知识库构建
知识库是提升LLM 推理准确性的关键组件。本系统构建了包含ArkTS 官方API
文档的知识库，涵盖String、Array、Map、Set 等常用类的方法说明。知识库构建过
程分为三个步骤：首先，收集ArkTS 官方文档和API 参考手册，确保信息的权威性
和准确性；其次，使用文本分块技术将长文档切分为较小的段落，每个段落包含一个
完整的方法说明；然后，采用OpenAI Embedding 或类似模型将文本段落转换为向量
表示，并存储到向量数据库中；最后，在运行时，根据方法签名检索最相关的文档片
段，作为LLM 的上下文输入。这种基于检索增强生成（RAG）的方法，有效提升了
LLM 对ArkTS API 的理解能力，减少了幻觉现象。
4.3.3 LLM 节点配置
LLM 节点是工作流的核心，负责实际的推理任务。该节点配置了精心设计的提
示词模板，包含系统提示词和用户提示词两部分。系统提示词定义了LLM 的角色和
任务，用户提示词包含具体的方法签名、检索到的文档片段和规则示例。LLM 节点
支持多种模型选择，包括GPT-4、DeepSeek-Chat、Qwen 等，方便进行模型对比实验。
此外，节点还启用了流式输出功能，虽然当前实现采用同步等待，但为后续异步优化
预留了空间。
4.3.4 Web 服务部署
Dify 平台提供了一键发布功能，将工作流包装为RESTful API 服务。发布后的服
务具有独立的URL，支持HTTP POST 请求，请求体包含方法签名等参数，响应体包
含生成的污点转移规则。服务支持并发请求处理，可以同时为多个分析引擎实例提
供服务。Dify 平台还提供了监控和日志功能，方便追踪服务运行状态、调试问题和
性能优化。此外，平台支持API 密钥认证，确保服务的安全性，防止未授权访问。通
过Dify 的Web 服务部署，智能污点转移系统可以轻松集成到现有的静态分析工具中，
无需复杂的部署和配置工作。

5.1 论文总结
本文针对鸿蒙移动应用代码安全分析的需求，以ArkTS 语言为研究对象，设计
并实现了一个基于指针分析的静态污点分析框架Arktan。随着HarmonyOS NEXT 操
作系统的发布和鸿蒙生态的快速发展，针对ArkTS 应用的安全分析工具研究具有重
要的理论意义和实践价值。本文的主要工作总结如下：
（1）构建了静态污点分析引擎及评估数据集。本文基于ArkAnalyzer 项目提供的
中间表示和控制流图，从零开始实现了针对ArkTS 语言的全程序指针分析算法。该
算法采用Andersen 指针分析算法框架，结合Worklist 算法实现了高效的指针流图构
建和调用图生成。在此基础上，本文设计了基于指针分析的污点分析算法，通过定义
污点源（source）、污点传播规则（transfer）和污点汇（sink）来实现对危险数据流的
追踪和检测。针对ArkTS 语言的特性，本文进行了多项适配工作：实现了对函数类型
变量等特性的支持；通过修改ArkAnalyzer 源码，解决了顶层代码处理和内置类方法
建模的问题；优化了DummyMain 方法的构建，确保能够正确处理主页面的build 方
法。
同时，为了提高框架的可扩展性和易用性，本文参考Tai-e 分析框架的设计思

NewMethod、onNewCallEdge 和onFinish 四个回调方法，分别对应指针分析的不同阶
段。研究人员可以通过实现这些接口来编写自定义插件，在不修改核心算法的前提下
实现特定的分析需求。基于该插件系统，本文实现了SourcePlugin、TaintTransferPlugin
和SinkPlugin 三个核心插件，分别负责污点源的标记、污点传播规则的处理和污点汇
的检测。这种设计使得污点分析逻辑与指针分析算法有机融合，同时保持了框架的灵
活性和可扩展性。

等方面还存在一些局限性。未来，我们将从以下几个维度对Arktan 进行持续改进和

的实现逻辑并生成相应的污点传播规则。
