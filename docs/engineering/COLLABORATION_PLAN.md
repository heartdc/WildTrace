# WildTrace 协作计划

## 目标

通过 GitHub issue、分支和 pull request 协作完成防御性 OpenHarmony 本地代码审计工具。所有工作只处理授权源码、固定版本和隔离环境；候选发现不等于漏洞确认。

## 三方职责

### 项目负责人（用户）

- 确认比赛范围、源码授权、固定版本和组件优先级。
- 决定是否接受高风险操作、真实代码构建和本地验证。
- 负责最终漏洞判断、CWE/CVE 定稿、补丁有效性判断和比赛报告签字。
- 负责协调合作伙伴账号、仓库权限和最终合并批准。

### Codex

- 负责主架构、FSM、证据模型、适配器、CLI、测试和集成。
- 维护 `PROJECT_STATE.md`、`CHANGELOG.md` 和架构文档。
- 负责 Clang/clang-tidy/其他引擎接入、结果一致性、源码快照和事务链。
- 负责把合作伙伴的规则或分析结果转换为统一 schema，并运行回归验证。

### 合作伙伴（GLM-5.3）

- 负责独立审阅漏洞规则、CWE 映射和误报风险。
- 负责提出 OpenHarmony 组件特定规则、调用链审查问题和基准样本建议。
- 负责对候选结果进行独立复核草稿，不直接宣布漏洞成立。
- 负责对现有实现做独立代码审查，优先关注遗漏、边界条件和比赛覆盖率。

## GitHub 工作流

1. 每项工作先建立一个 issue，写明目标、输入、输出、风险和验收条件。
2. 每个参与者使用独立分支，不直接向 `master` 推送。
3. 分支命名：`codex/<topic>`、`glm/<topic>`、`user/<topic>`。
4. 一个 PR 只解决一个主题，避免把规则、架构和文档混在一起。
5. PR 必须包含测试结果、源码/版本范围、证据边界和未完成事项。
6. 涉及 `ohvul/workflow`、`ohvul/domain`、证据校验和安全边界的 PR 必须由用户或 Codex 复核后合并。
7. GLM 产生的规则建议先进入 issue 或 PR 草稿，经独立测试后再合并。
8. 合并前运行完整离线测试；失败或输入上下文缺失不能被标记为漏洞不存在。

## 冲突处理

- 不允许两个分支直接覆盖对方的规则、证据 schema 或状态迁移。
- 规则争议先保留为候选和复核问题，不通过模型投票自动定案。
- 架构冲突由 FSM、证据可复现性和安全边界优先级裁决。
- 任何模型输出都必须经过 schema 校验、测试和人工审核。

## 当前协作切分

- Codex：继续维护真实 OpenHarmony 组件输入、Clang/clang-tidy 适配和结果事务链。
- GLM-5.3：独立审阅 cameraApp 候选规则、提出第二批 OpenHarmony 语义规则和误报反例。
- 用户：提供或确认固定版本范围，审核高风险候选和决定哪些组件进入比赛基准。

## 审查后的重新规划

当前优先级从“继续增加功能”调整为“先修结果正确性，再扩大真实分析范围”。

### 阶段 A：适配层正确性冻结

Codex 负责修复分片重复 `alert_id`、引擎来源区分、外部结果完整校验、分片直接路径读取和快照一致性。GLM-5.3 可以独立审查这些修改并提交测试或审查意见，但不直接改 `workflow/`、`domain/` 或证据校验核心。

### 阶段 B：固定组件分析 profile

Codex 负责 `OpenHarmony-complete` 的组件 profile、固定 commit、include/define、编译参数和多文件运行链。用户确认授权范围和固定版本。GLM-5.3 负责检查 profile 是否遗漏依赖，并审查输入错误是否被正确区分。

### 阶段 C：双引擎组件试验

先在一个完整组件上统一 Clang Analyzer 和 clang-tidy，再选择一个跨函数工具进行小规模对比。GLM-5.3 可以编辑引擎解析器测试、规则映射和结果比较工具；Codex 负责统一 schema、证据链和主 CLI 集成。

### 阶段 D：两个高价值漏洞族

优先 UAF/生命周期和权限/IPC 边界。GLM-5.3 负责提出规则、反例和测试草稿；Codex 负责实现适配、接入 FSM 和证据模型；用户负责最终安全语义判断。

### 阶段 E：补丁、评测和交付

完成补丁前后比较、人工标注、性能矩阵、报告和演示。GLM-5.3 可编辑 benchmark、报告模板和分析说明；Codex 负责结果一致性和发布前回归；用户批准最终报告。

## 编辑权限边界

GLM-5.3 可以直接编辑：

- `tests/`
- 规则映射和引擎解析器的非核心模块
- benchmark、样本模板和评测脚本
- 技术说明和 Demo 文档

GLM-5.3 必须通过 PR 提交、不得直接改动：

- `ohvul/workflow/`
- `ohvul/domain/`
- `ohvul/verification_link.py`
- `ohvul/verify.py`
- `ohvul/cli.py` 的事务和 checkpoint 主链
- 安全边界、候选状态和人工审核门控

每个 PR 必须说明实际源码范围、测试命令、输入错误处理和是否改变候选/确认语义。
