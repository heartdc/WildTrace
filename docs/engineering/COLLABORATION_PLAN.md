# WildTrace 协作计划

## 目标

通过 GitHub issue、分支和 pull request 协作完成防御性 OpenHarmony 本地代码审计工具。所有工作只处理授权源码、固定版本和隔离环境；候选发现不等于漏洞确认。

## 三方职责

### 项目负责人（用户）

- 确认比赛范围、源码授权、固定版本和组件优先级。
- 决定是否接受高风险操作、真实代码构建和本地验证。
- 负责最终漏洞判断、CWE/CVE 定稿、补丁有效性判断和比赛报告签字。
- 负责协调合作伙伴账号、仓库权限和最终合并批准。

### Codex

- 负责主架构、FSM、证据模型、适配器、CLI、测试和集成。
- 维护 `PROJECT_STATE.md`、`CHANGELOG.md` 和架构文档。
- 负责 Clang/clang-tidy/其他引擎接入、结果一致性、源码快照和事务链。
- 负责把合作伙伴的规则或分析结果转换为统一 schema，并运行回归验证。

### 合作伙伴（GLM-5.3）

- 负责独立审阅漏洞规则、CWE 映射和误报风险。
- 负责提出 OpenHarmony 组件特定规则、调用链审查问题和基准样本建议。
- 负责对候选结果进行独立复核草稿，不直接宣布漏洞成立。
- 负责对现有实现做独立代码审查，优先关注遗漏、边界条件和比赛覆盖率。

## GitHub 工作流

1. 每项工作先建立一个 issue，写明目标、输入、输出、风险和验收条件。
2. 每个参与者使用独立分支，不直接向 `master` 推送。
3. 分支命名：`codex/<topic>`、`glm/<topic>`、`user/<topic>`。
4. 一个 PR 只解决一个主题，避免把规则、架构和文档混在一起。
5. PR 必须包含测试结果、源码/版本范围、证据边界和未完成事项。
6. 涉及 `ohvul/workflow`、`ohvul/domain`、证据校验和安全边界的 PR 必须由用户或 Codex 复核后合并。
7. GLM 产生的规则建议先进入 issue 或 PR 草稿，经独立测试后再合并。
8. 合并前运行完整离线测试；失败或输入上下文缺失不能被标记为漏洞不存在。

## 文件所有权建议

| 区域 | 默认负责人 | 复核人 |
|---|---|---|
| `ohvul/workflow/`、`ohvul/domain/` | Codex | 用户 |
| `ohvul/engine_*`、适配器和 CLI | Codex | GLM-5.3 |
| 规则建议、CWE 映射和基准草稿 | GLM-5.3 | Codex + 用户 |
| `docs/analysis/`、比赛报告框架 | 用户 + Codex | GLM-5.3 |
| 人工复核、CVE 对应和补丁结论 | 用户 | Codex/GLM 提供证据 |

## 冲突处理

- 不允许两个分支直接覆盖对方的规则、证据 schema 或状态迁移。
- 规则争议先保留为候选和复核问题，不通过模型投票自动定案。
- 架构冲突由 FSM、证据可复现性和安全边界优先级裁决。
- 任何模型输出都必须经过 schema 校验、测试和人工审核。
