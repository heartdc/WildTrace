## 摘要

OpenHarmony 主干包含 471 个项目与 200 余个第三方组件，C/C++ 代码总量超过 3,400 万行。在这样的规模上，人工代码审计与模糊测试"效率低、成本高，且难以覆盖全部代码"。赛题要求工具具备从漏洞识别到报告生成的六项端到端能力：大规模自动化分析、输出 CWE/CVE 信息、产出可执行 PoC、评估严重程度与影响范围、提供修复建议、生成漏洞报告。

本作品实现了满足这六项能力的自动化系统 WildTrace。检测层含 13 个模式族（通用 C/C++ 10 个 + FFI 特有 3 个）和 Joern CPG 选配引擎，覆盖缓冲区溢出、空指针解引用、整数溢出、UAF/双释放、信息泄露、拒绝服务等漏洞类型。核心创新是指针状态模型：对每个指针变量建立 Null/NonNull/MaybeNull 三态时间线，检测输出为分层的可证明性结论，每个不发射的访问在抑制日志中记录原因——使 68 万行代码上 2,662 条候选到 13 条高价值线索的收敛过程逐条可审计。验证层在官方完整树构建的真实库上以对照矩阵、双 ASLR gdb 帧归因和确定性判读技术（分配器填充差分、ASan 上限定点拦截）将候选升级为可评审证据，证实与证伪双向归档。影响评估覆盖 6 个版本分支并区分证据层级，三出口一致性由契约测试锁定。

在 OpenHarmony 分布式软总线（68 万行）上产出 2,662 条候选线索；在真实库上完成 6 个高价值目标的验证，其中 3 项新发现获得运行级 SIGSEGV 证据（IPC、HiAppEvent 已提交漏洞奖励计划，UDMF 材料齐备待提交），另有 1 项 bluetooth 服务端空指针（材料齐备待提交，未纳入 20 案统计）、2 项经运行排除并如实归档。另向漏洞奖励计划提交 15 张已公开 CVE 的下游缺口工单，合计 17 单评审中。20 个案例全部附 PoC 代码、修复补丁和分支影响判定。检测器自身质量由三层独立评估度量：严格修复对回放（GT1-GT3 三对全部通过）、种子化召回基准（开发集 11/11）、交叉复核（八项发现全部经复现后修复）。全量回归 1,248 项、1,242 项通过。

**关键词**：OpenHarmony；漏洞挖掘；静态分析；PoC 生成；分支影响分析；证据链

## 第一章 作品概述

### 1.1 背景分析

#### 1.1.1 OpenHarmony 的安全挑战

OpenHarmony 是开放原子开源基金会孵化及运营的开源项目，由华为捐赠核心代码、社区共建，是 HarmonyOS 生态的技术底座。据官方披露，OpenHarmony 生态设备规模已达亿级，覆盖手机、平板、穿戴、智能家居、车机等多种设备形态。

与传统移动操作系统不同，OpenHarmony 采取了"全栈开源 + 多语言并存"的技术路线：系统组件以 C/C++ 实现并经由内部接口暴露能力，应用层语言历经 Java → ArkTS → 仓颉的演进，分布式能力则通过软总线等中间件横向打通。其官方代码仓库包含 471 个项目，主干以版本快照方式引入 200 余个第三方组件（ffmpeg、openssl、curl、cJSON 等），代码库规模庞大、复杂度高。

这种异构性带来了两方面的安全挑战：

**已知漏洞的下游暴露**。主干以旧版本快照引入第三方组件，上游修复 CVE 后 OpenHarmony 是否真正回移**不透明**——回移经常不走上游 commit，而是以仓库根目录 `Fix-/Backport-CVE-*.patch` 文件 + BUILD.gn 的形式存在，导致基于 commit 或版本号比对的工具系统性误报。"哪些已知漏洞在 OpenHarmony 上仍然开放"这一基础问题，此前缺乏可靠的自动化回答手段。

**新攻击面的出现**。随着应用层语言演进，应用与仍以 C/C++ 实现的系统组件之间出现了跨语言调用边界——结构化参数（如 `CArrXxx = {head, size}`）在边界对端失去类型系统的非空和长度保证。这个边界此前没有被自动化工具覆盖。

#### 1.1.2 赛题对工具能力的要求

赛题要求工具"能够识别各类安全漏洞类型（缓冲区溢出、空指针解引用、整数溢出、UAF、信息泄露、权限提升、拒绝服务、逻辑漏洞等）"并完成从识别到报告的全流程。这对工具架构提出了明确约束：单一模式扫描器只能覆盖部分类型，而组合多个独立工具又会在数据一致性和误报控制上失控。工具必须是多层检测管线，且每层的收敛过程可审计。

赛题同时强调"误报问题会有对应的负向扣分"和"PoC 代码的可复现性和稳定性会影响评分"。前者要求工具具备系统性误报治理能力而非仅靠人工筛选；后者要求 PoC 不只是可编译的代码片段，而是能在目标环境中实际触发的验证程序。

**赛题六能力与本作品章节映射**：

| 赛题能力 | 本作品对应 | 章节 |
|---|---|---|
| 1. 大规模自动化分析识别漏洞 | 13 模式族检测管线（autopilot v3 十层 + Joern CPG 选配） | §2.2 |
| 2. CWE/CVE 输出 | 逐案 CWE 候选 + 16 案 CVE 编号映射（kb 联接） | §2.2.4 |

### 1.2 相关工作

#### 1.2.1 移动操作系统原生接口面的自动化挖掘

FANS（USENIX Security 2020）自动化收集 Android 原生系统服务的 Binder 接口（含深层嵌套），经语义建模与依赖处理后定向模糊测试，发现 168 个问题。NASS（USENIX Security 2025）以反序列化引导的接口提取与覆盖反馈将此类挖掘扩展至全部 Android 原生服务。两代工作确立了"接口提取 → 语义建模 → 定向验证"的方法论共识，但其对象全部为 Android/Binder。本作品面对的 CJ FFI 接口与 Binder 接口同构（应用语言到 C++ 的结构化参数边界），OpenHarmony 侧此前无对应工具。

#### 1.2.2 跨语言 FFI 边界安全

Qin 等（IEEE S&P 2020）对 Rust 程序 unsafe 代码的实证研究表明"安全语言的 unsafe 边界"是真实且反复被证明的漏洞来源。Mergendahl 等（NDSS 2022）定义了跨语言攻击威胁模型，证明 C/C++ 侧的内存加固可被 FFI 对端绕过。该方向证实了语言边界的风险通则，但均为实证或防御视角，对象为 Rust/Go。

#### 1.2.3 已知漏洞与补丁存在性判定

VUDDY（ICSE 2017）以补丁粒度的代码克隆匹配检测已修复漏洞是否仍存在。Zhang 等（USENIX Security 2018）在二进制中判定特定安全补丁是否存在。两者回答"漏洞代码是否在场"，但不回答下游是否以自有形态真正回移（如 OpenHarmony 的 patch 文件形态），也不为每个结论生成运行级证据。

#### 1.2.4 OpenHarmony 安全研究现状

ArkAnalyzer（ICSE 2025 SEIP）与 HapCheck（ICSE 2026 SEIP）分别提供 ArkTS/HAP 应用层的静态分析与缺陷检测，均位于应用层。通用静态扫描器（Semgrep/CodeQL/clang-tidy）不掌握 OpenHarmony 特有的结构体契约与回移形态，在本场景中或无法触达或误报偏高。

## 第二章 作品设计与实现

### 2.1 作品使用技术及原理

#### 2.1.1 多模式族检测：通用 C/C++ 与 FFI 契约感知

检测层包含 13 个模式族。通用族（P4 不安全拷贝、P5 栈溢出、P6 空指针、P7 分配溢出、P8 UAF、P9 格式串、跨函数 UAF，及 Joern J4/J6/J8）适用于任意 C/C++ 代码。FFI 特有族从仓颉 FFI 的 ABI 结构体契约推导。

**FFI 特有的三类模式族**如下：

**F1 数组头长失配**。仓颉侧以 `{head, size}` 结构对传递数组——`CArrStr = { CStr* head; int64_t size; }`。当 head=NULL 而 size>0 时，C 侧接收函数的循环 `for (int i = 0; i < size; i++) head[i]` 直接对空指针解引用。这是最普遍的形态，IPC 的 `WriteByteArray` 和 HiAppEvent 的 `AddWatcher` 均为此型。检测器扫描接收此类参数的函数体内是否存在未判空的循环遍历。

**F2 嵌套指针**。参数包结构（如 `CParameters = {valueType, key, value, size}`）中 value 指向的内部数组在分发前未判空。这比外层 head 空指针深一级——需要跟踪结构体成员的解引用链。AVSession 的 `SendCommonCommand` 的 CArray→CParameters 分发即为此型。

**F3 负长度下溢**。size<0 经隐式转换为 size_t/uint32 的巨值（4,294,967,295 级），导致巨循环或巨拷贝。检测器识别 size 参数在有符号/无符号转换后直接用于循环边界或分配的场景。

每条候选附带可解释的置信度因子（如"+25 9 处 post-free 使用；+10 post-free 写入"）与触发提示（如"`{head=NULL, size=1}`"），供分诊与 PoC 生成直接使用。

#### 2.1.2 指针状态模型与可证明性排序

这是检测层的核心创新。对每个指针/智能指针变量建立 **Null / NonNull / MaybeNull 三态时间线**——按源码顺序记录赋值、判空、解引用事件，据此计算每个解引用点的状态：

- **Null（确定性崩溃）**：到达该解引用点时指针必为空。例如 `p = NULL; p->field = 1;`。
- **MaybeNull（待论证）**：到达该点时指针可能为空也可能不为空，取决于运行时路径。例如未经判空的函数参数。
- **NonNull（安全，不发射）**：到达该点时指针必不为空。例如 `if (p != NULL) { p->field = 1; }`。

守卫确认规则经交叉复核收窄为**独立无条件 return**——只有 `if (!p) { return; }` 这种顶层、无嵌套条件的 return 才能确认守卫后的访问安全。条件 return（`if (!p) { if (flag) return; }`）和 goto 不确认安全，因为控制流可能绕过守卫到达后续访问。

抑制日志记录每个被判定为安全而不发射的访问及其原因，使收敛过程逐条可审计——误报治理从"阈值调多少"转变为"状态机论证是否成立"。

#### 2.1.3 宏守卫识别与误报抑制

OpenHarmony 代码大量使用前缀化的真值检查宏族（`AUTH_/TRANS_/NSTACKX_CHECK_AND_RETURN*(cond, ...)`）做空指针防护。本作品实现**按宏名极性判定**的守卫识别：

- 裸变量式（`CHECK_*(param, ...)`）与前缀族一律识别为防护；
- 条件式（`param ==/!= NULL`）仅当宏名携带 RETURN/RET 语义（返回型守卫）时才抑制；
- `CHECK_INVOKE(param != nullptr)` 这类"非空才动"的调用型宏不构成空防护，不抑制。

该设计由已知答案回放驱动，在 68 万行实测中精确消除 229 条误报。

#### 2.1.4 P8 分支/闭包敏感化

同函数 UAF 启发式对异步回调型代码存在两类系统性误报：

**分支互斥 free**。错误分支中的 `free(p); return;` 导致后续使用被误报为 UAF——但 return 已保证控制流不会到达后续代码。抑制条件收窄为：free 所在分支以独立无条件 return 终止（同行无 if/for/while/else 且括号平衡）。

**回调闭包**。使用位于 lambda 体内而 free 在闭包外——注册型回调的生命周期与当前执行不同步。立即调用闭包（IIFE `}()`）不抑制，因为它在同一执行流中。

dsoftbus 实测中旧启发式产出 448 条候选，加入抑制后降至 69 条。移除的 379 条经抽查确认为错误分支路径或闭包生命周期差异所致，2,383 个使用点逐条记录抑制原因。

#### 2.1.5 知识库联接与版本影响判定

以 CVE 编号联接 cvelistV5 知识库记录，按边界语义（起点 ≤ 基线 < 修复点）逐分支判定。判定遵循三条规则：

1. **不跨组件借用基线**：某分支缺该组件数据时判 ？，不用其他组件版本号顶替；
2. **？不是安全结论**：待定格显式标注缺失证据与升级路径，而非推断填充；
3. **证据分级**：🔴 证实 affected / — 证实不受影响 / ？ 待定。

### 2.2 系统方案

系统由三段管线（收割 → 分诊 → 验证）与两条辅线（1-day 缺口判定、检测质量评估）组成。

![图 1 系统总体架构](assets/fig1_architecture.png)

#### 2.2.1 T1 代码面收割

扫描目标仓库全集（136 个克隆仓中 63 个含 FFI 源面 / 173,901 行 / 272 秒），提取 FFI 导出函数符号（`FfiOHOS*` 族）、ABI 结构体契约与调用位置，形成带高危分级的接口清单（380 条 lead，高危 84）。收割结果直接服务于 T2 分诊排序。

#### 2.2.2 T2 模式族分诊与验证客户端合成

按模式族对候选分桶分批，对每个候选**合成逐字对齐 ABI 的验证客户端**：本地构造 C 结构、dlopen 打开真库导出符号直调，内含对照/候选/变体三组输入矩阵，不复制任何目标实现代码。

验证客户端的设计要点：

- **对照组**输入合法参数（`{head=有效指针, size=1}`），验证客户端本身无 bug；
- **候选组**输入畸形参数（`{head=NULL, size=1}`），触发目标缺陷；
- **变体组**输入边界参数（`{head=NULL, size=0}`），定位缺陷的精确条件。

对置信度 ≥50 的候选管线自动生成模板 PoC；LLM PoC 生成作为增强路径（见 4.4）。

#### 2.2.3 T3 真库验证阶梯

![图 2 真库验证阶梯](assets/fig2_ladder.png)

将候选升级为可评审证据的四级阶梯：

**第一级：官方完整树构建**。以 repo manifest 同步的官方完整树（471+ 项目）构建目标库，零 FFI 源码改动。这杜绝了隔离树 mock 补丁对崩溃归因的污染——如果用了 mock 树，崩溃可能来自 mock 代码而非目标缺陷。

**第二级：对照矩阵运行**。验证客户端在真库上运行三组输入。缺陷必须精确限定于畸形组合：对照组合法返回、候选组触发崩溃。如果对照组也崩溃，说明验证客户端自身有 bug，不是目标缺陷。

**第三级：双 ASLR gdb 帧归因**。两次不同地址布局下复现，崩溃帧必须映射落在目标库内（file_offset 级）——排除 musl 运行库与适配层的干扰。如果崩溃帧在 libc 而非目标库，则不能归因为目标缺陷。

**第四级：结论与归档**。证实 → 生成工单材料提交漏洞奖励计划。证伪（FFI 层参数检查拦截了全部畸形输入）或隔离限制 → 如实归档。证伪同样有价值——它关闭了候选的产品影响主张，避免无效工单浪费评审资源。

每案记录库指纹（sha256/BuildID/导出符号数）、构建溯源（裸仓 HEAD 构建提交 + manifest 分支）与红线声明（隔离环境、无产品服务、自定义构建配置），形成完整证据包。

**确定性判读技术**。配套两项不依赖 MSan 的判读方法：

- **分配器填充差分**：同一畸形输入在两种堆填充字节（如 0xAA vs 0xBB）下运行，输出帧校验和不同即证明未初始化堆字节流出了分配边界（rscc 案运行级实证）。
- **ASan 分配上限定点拦截**：设置分配上限后 ASan 报告直接指向无界分配行（iamf 案运行级实证：count_label=0x0FFFFFFF 触发 ~2.1GB 分配请求）。

#### 2.2.4 1-day 缺口判定与影响矩阵

## 第四章 创新性说明

### 4.1 指针状态模型：从告警到可证明性分层

传统静态扫描器输出的是"疑似告警"——告警数量取决于阈值调校，使用者无法判断某条告警为什么被发出（或没被发出）。本作品的核心检测创新是指针状态模型：对每个指针变量建立三态时间线，检测输出为分层的可证明性结论，每个不发射的访问在抑制日志中记录原因。

这使得 68 万行代码上 2,662 条候选到 13 条高价值线索的收敛过程**逐条可审计**——使用者可以检查任何一条被抑制的访问，验证抑制理由是否成立。误报治理从"阈值调多少"转变为"状态机论证是否成立"。

守卫确认规则经交叉复核反例收窄为独立无条件 return。条件 return（`if (!p) { if (flag) return; }`）和 goto 不确认安全，因为控制流可能绕过守卫到达后续访问——这类反例已入回归测试锁定。

### 4.2 真库验证阶梯与确定性判读

将"发现"与"可评审证据"分级的四级验证阶梯：官方完整树零源码改动构建、对照矩阵运行、双 ASLR gdb 帧归因、结论与归档。配套两项确定性判读技术：

- **分配器填充差分**：同一畸形输入在两种填充字节下输出帧校验和不同，证明未初始化堆字节流出分配边界。不依赖 MSan 全链插桩。
- **ASan 分配上限定点拦截**：设置分配上限后 ASan 报告直接指向无界分配行，不需要实际触发 OOM。

UDMF 案的 round-trip 论据（getter 合法输出回喂 setter 必崩）将可达性论证从"存在恶意调用者"提升到"正常 API 使用模式即触发"。

### 4.3 检测质量的可测量化

漏洞挖掘工具通常只报告产出、不度量自身。本作品建立了三层检测质量评估协议：

1. **严格修复对**：应用真实修复后检测必须"命中→消失、零误伤"——不是在合成样本上测试，而是在真实已修复漏洞的代码上验证。
2. **种子化召回基准**：正向负向分离、独立文件归属、反向测试锁定——基准本身曾存在归属缺陷，经交叉复核纠出后重写。
3. **交叉复核**：八项发现全部复现并修复入回归——检测器自身的可信度成为可测量、可被独立检验的对象。

### 4.4 LLM 的受控集成：生成增强与"供信号不裁决"

**生成侧**——四步闭环：状态模型语义注入（P6 输出进提示词）→ 编译反馈环（失败 stderr 回喂重试）→ ASan 执行检测 → 真库 dlopen 验证。

**治理侧**——LLM 永不产生漏洞结论：强制 undetermined 出口、路径包含与注入防御、危险 API 输出屏蔽（16 项安全测试）、密钥仅运行时环境变量。

26 组审查队列全部执行完毕（46 次调用 / 66,782 tokens），26/26 草稿 final_verdict 均为 undetermined——纪律在规模下不变形。

### 4.5 证据工程

20 案证据链含五段式结构（源码位置/CWE/触发条件/PoC/影响评估），三出口一致性由契约测试锁定（工作台/矩阵/报告同输入同判定），证据质量成为可回归的工程属性。分支影响矩阵对 20 案 × 6 分支全部录入判定并区分证据层级。

- **质量保证**：三层独立评估（严格修复对、种子化基准、交叉复核）加全量 1,248 项回归测试（1,242 项通过）。

**适用范围**：真库级验证在隔离自定义配置下完成，产品环境可达性为后续独立验证。访问识别为词法层，AST 级识别为后续演进方向。影响矩阵中钉版联接和符号探测类格子的证据强度弱于检出/复级实证。cfhd 案需上游系数样本、nvdec 需 GPU 环境、curl 案需特定 TLS 后端，均如实标注验证边界。

**后续方向**：结构感知的边界模糊测试、AST 级访问识别、产品级可达性验证。
