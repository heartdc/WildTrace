## 摘要

OpenHarmony 主干包含 471 个项目与 200 余个第三方组件，代码量超过 3400 万行。在这样的规模上，人工代码审计与模糊测试"效率低、成本高，且难以覆盖全部代码"（赛题原文）。赛题要求工具具备从漏洞识别到报告生成的六项端到端能力：大规模自动化分析识别漏洞、输出 CWE/CVE 信息、产出可执行 PoC、评估严重程度与影响范围、提供修复建议、生成漏洞报告。

本作品实现了满足这六项能力的自动化系统 WildTrace。检测层含 13 个模式族（通用 C/C++ 10 个 + FFI 特有 3 个）和 Joern CPG 选配引擎，覆盖缓冲区溢出、空指针解引用、整数溢出、UAF/双释放、信息泄露、拒绝服务等类型；验证层在官方完整树构建的真实库上以对照矩阵与双 ASLR 帧归因产出可评审证据；影响评估覆盖 6 个版本分支并区分证据层级；报告生成自动投影统一数据源，三出口一致性由契约测试锁定。

在 OpenHarmony 分布式软总线（68 万行）上产出 2,662 条候选线索，经指针状态模型语义收敛至 13 条高价值线索；在真实库上完成 6 个高价值目标的验证，其中 4 项新发现获得运行级 SIGSEGV 证据（2 项已提交漏洞奖励计划、2 项材料齐备待提交）、2 项经运行排除并如实归档。另向漏洞奖励计划提交 15 张已公开 CVE 的下游缺口工单，合计 17 单评审中。20 个案例全部附 PoC 代码、修复补丁和分支影响判定。检测器自身质量由三层独立评估度量：严格修复对回放（GT1-GT3 三对全部通过）、种子化召回基准（开发集 11/11）、外部独立复审（八项发现全部修复）。全量 1,191 项回归测试通过。

**关键词**：OpenHarmony；漏洞挖掘；静态分析；PoC 生成；分支影响分析；证据链

## 第一章 作品概述

### 1.1 背景与问题

#### 1.1.1 大规模代码库上的自动化漏洞检测需求

赛题要求工具"能够识别各类安全漏洞类型（缓冲区溢出、空指针解引用、整数溢出、UAF、信息泄露、权限提升、拒绝服务、逻辑漏洞等）"并完成从识别到报告的全流程。这对工具架构提出了明确约束：单一模式扫描器只能覆盖部分类型，而组合多个独立工具又会在数据一致性和误报控制上失控。工具必须是多层检测管线，且每层的收敛过程可审计。

赛题同时强调"误报问题会有对应的负向扣分"和"PoC 代码的可复现性和稳定性会影响评分"。前者要求工具具备系统性误报治理能力而非仅靠人工筛选；后者要求 PoC 不只是可编译的代码片段，而是能在目标环境中实际触发的验证程序。

#### 1.1.2 已知漏洞的下游暴露问题

OpenHarmony 主干以版本快照方式引入第三方组件，上游修复 CVE 后下游是否真正回移**不透明**——回移经常不走上游 commit，而是以仓库根目录 `Fix-/Backport-CVE-*.patch` 文件的形式存在，导致基于 commit 或版本号比对的工具系统性误报。"哪些已知漏洞在 OpenHarmony 上仍然开放"这一基础问题，此前缺乏可靠的自动化回答手段。

#### 1.1.3 新攻击面的探索方向

在通用漏洞检测与已知漏洞缺口判定之外，本作品以仓颉 FFI（外部函数接口）边界为特色探索方向。随着 HarmonyOS NEXT 完成应用层语言演进，应用与仍以 C/C++ 实现的系统组件之间出现了跨语言调用边界——结构化参数在边界对端失去类型系统的非空和长度保证。这构成了一个此前未被自动化工具覆盖的检测面。

**赛题六能力与本作品章节映射**：

| 赛题能力 | 本作品对应 | 章节 |
|---|---|---|
| 1. 大规模自动化分析识别漏洞 | 13 模式族检测管线（autopilot v3 十层 + Joern CPG 选配） | §2.2 |
| 2. CWE/CVE 输出 | 逐案 CWE 候选 + 15 案 CVE 编号映射（kb 联接） | §2.2.4 |
| 3. 可执行 PoC | 20/20 案附 PoC 代码；LLM PoC 四步闭环 | §2.2.3/§4.5 |
| 4. 严重程度与影响范围 | 20 案 × 6 分支影响矩阵（证据分层）+ 严重度分级 | §2.2.4 |
| 5. 修复建议/补丁 | 20/20 案附 patch.diff 或修复建议 | 各案 case.json |
| 6. 漏洞报告生成 | competition_report 自动生成（含源码位置/详情/PoC/影响/修复） | §2.3 |

### 1.2 相关工作

#### 1.2.1 移动操作系统原生接口面的自动化挖掘

FANS（USENIX Security 2020）自动化收集 Android 原生系统服务的 Binder 接口，经语义建模与依赖处理后定向模糊测试。NASS（USENIX Security 2025）以反序列化引导的接口提取将此类挖掘扩展至全部 Android 原生服务。两代工作确立了"接口提取 → 语义建模 → 定向验证"的方法论，但对象全部为 Android/Binder。本作品面对的 CJ FFI 接口与 Binder 接口同构（应用语言到 C++ 的结构化参数边界），OpenHarmony 侧此前无对应工具。

#### 1.2.2 跨语言 FFI 边界安全

Qin 等（IEEE S&P 2020）对 Rust 程序 unsafe 代码的实证研究表明"安全语言的 unsafe 边界"是真实且反复被证明的漏洞来源；Mergendahl 等（NDSS 2022）定义了跨语言攻击威胁模型。该方向证实了语言边界的风险通则，但均为实证或防御视角，对象为 Rust/Go。

#### 1.2.3 已知漏洞与补丁存在性判定

VUDDY（ICSE 2017）以补丁粒度的代码克隆匹配检测已修复漏洞是否仍存在；Zhang 等（USENIX Security 2018）在二进制中判定特定安全补丁是否存在。两者回答"漏洞代码是否在场"，但不回答下游是否以自有形态真正回移（如 OpenHarmony 的 patch 文件形态），也不为每个结论生成运行级证据。

#### 1.2.4 OpenHarmony 安全研究现状

ArkAnalyzer（ICSE 2025 SEIP）与 HapCheck（ICSE 2026 SEIP）分别提供 ArkTS/HAP 应用层的静态分析与缺陷检测，均位于应用层。通用静态扫描器（Semgrep/CodeQL/clang-tidy）不掌握 OpenHarmony 特有的结构体契约与回移形态，在本场景中或无法触达或误报偏高。

### 1.3 本文贡献

1. **多层检测管线与语义收敛**：13 个模式族覆盖七类漏洞，经指针状态模型将 68 万行代码上的 2,662 条候选收敛至 13 条高价值线索，每个不发射的访问在抑制日志中记录原因。
2. **真库验证阶梯**：在官方完整树构建的真实库上以对照矩阵、双 ASLR 帧归因和确定性判读技术将候选升级为可评审证据；证实与证伪双向归档。
3. **20 案证据链与分支影响矩阵**：4 项新发现获运行级 SIGSEGV 证据，15 张 CVE 缺口工单已提交，20 案 × 6 分支全部判定并区分证据层级。
4. **三层检测质量评估**：严格修复对回放、种子化召回基准、外部独立复审，将检测器自身可信度变为可测量对象。

## 第二章 作品设计与实现

### 2.1 检测原理

#### 2.1.1 多模式族检测：通用 C/C++ 与 FFI 契约感知

检测层包含 13 个模式族。通用族（P4 不安全拷贝、P5 栈溢出、P6 空指针、P7 分配溢出、P8 UAF、P9 格式串、跨函数 UAF，及 Joern J4/J6/J8）适用于任意 C/C++ 代码。FFI 特有族（F1 数组头长失配、F2 嵌套指针、F3 负长度下溢）从仓颉 FFI 的 ABI 结构体契约推导——`{head, size}` 对中 head=NULL 而 size>0 时，C 侧循环直接解引用；参数包中 value 指向的内部数组在分发前未判空；size<0 经隐式转换变为巨值。

每条候选附带可解释的置信度因子（如"+25 9 处 post-free 使用"）与触发提示（如"`{head=NULL, size=1}`"），供分诊与 PoC 生成直接使用。

#### 2.1.2 宏守卫识别与误报抑制

OpenHarmony 代码大量使用前缀化的真值检查宏族做空指针防护。本作品实现按宏名极性判定的守卫识别：裸变量式与前缀族一律识别为防护；条件式仅当宏名携带 RETURN 语义时才抑制。该设计由已知答案回放驱动，在 68 万行实测中精确消除 229 条误报。

#### 2.1.3 知识库联接与版本影响判定

以 CVE 编号联接 cvelistV5 知识库记录，按边界语义（起点 ≤ 基线 < 修复点）逐分支判定。判定遵循三条规则：不跨组件借用基线；待定格显式标注缺失证据而非推断填充；证据分级（证实/排除/待定）。

### 2.2 系统方案

系统由三段管线（收割 → 分诊 → 验证）与两条辅线（1-day 缺口判定、已知答案回放）组成。

![图 1 系统总体架构](assets/fig1_architecture.png)

#### 2.2.1 T1 代码面收割

扫描目标仓库全集（136 仓 / 173,901 行 / 272 秒），提取 FFI 导出函数符号、ABI 结构体契约与调用位置，形成带高危分级的接口清单（380 条 lead，高危 84）。

#### 2.2.2 T2 模式族分诊与验证客户端合成

按模式族对候选分桶，对每个候选合成逐字对齐 ABI 的验证客户端：本地构造 C 结构、dlopen 打开真库导出符号直调，内含对照/候选/变体三组输入矩阵。对置信度 ≥50 的候选管线自动生成模板 PoC。

#### 2.2.3 T3 真库验证阶梯

![图 2 真库验证阶梯](assets/fig2_ladder.png)

1. **官方完整树构建**：repo manifest 同步的官方完整树构建目标库，零 FFI 源码改动；
2. **对照矩阵运行**：验证客户端在真库上运行对照/候选/变体三组，缺陷必须精确限定于畸形组合；
3. **双 ASLR gdb 帧归因**：两次不同地址布局下复现，崩溃帧必须映射落在目标库内（file_offset 级）；
4. **结论与归档**：证实 → 生成工单材料；证伪或隔离限制 → 如实归档，关闭候选的产品影响主张。

#### 2.2.4 1-day 缺口判定与影响矩阵

对 20 案 × 6 分支生成证据分层影响矩阵：主表为分支判定（严格口径，仅计 per-branch 证据），另设独立标注的上游版本预测区。第三方 16 案经分支钉版联接判定（manifest 钉版 → gitcode README 版本实证 → kb 受影响区间）；OH 原生四案经符号级探测判定（漏洞函数逐分支存在性）。

三个出口（工作台/影响矩阵/漏洞报告）由契约测试锁定同输入同判定：版本信息可形成风险预测但不代替分支证据；单一分支判定不扩散到其他分支。

#### 2.2.5 检测质量评估

以历史已知漏洞回放检测器度量盲点与误报；在此之上叠加种子化召回基准（正向种子 11 个 + 负向种子 5 个，独立文件归属，负种子声明须静默的模式族）和 P8 分支/闭包敏感化（对异步回调型代码的两类系统性误报实现带因抑制）。

### 2.3 软件运行流程

工具提供 CLI 与本地工作台双入口。

- **CLI**：`python -m ohvul.autopilot <源码根>` 一条命令完成 10 层管线，输出 findings.json/md 与 pocs/；
- **本地工作台**（React + FastAPI，仅绑 127.0.0.1）：扫描任务管理、候选分诊、报告预览与 PoC 管理；
- **安全契约**：全流程仅本地读取、不执行目标代码（运行时验证轨道限定单一案例 + 隔离沙箱）、不持久化密钥。

工程规模：Python 10 层管线 + 前端工作台，1,191 项回归测试通过，CI 全绿。

#### 3.2.2 真库验证

| 目标 | 接口 | 畸形输入 | 结果 |
|---|---|---|---|
| IPC | WriteByteArray | data=NULL, len>0 | SIGSEGV，帧归因库内 → 已提单 |
| HiAppEvent | AddWatcher | head=NULL, size>0 | SIGSEGV，帧归因库内 → 已提单 |

新发现的安全影响定性：缺陷位于系统侧代码（系统框架 FFI 库或系统服务进程），受害面为使用该系统 API 的应用。后果表述为"可用性破坏与潜在内存安全影响"，最终价值以漏洞奖励计划评审结果为准。

#### 3.2.3 检测质量三层评估

**严格修复对回放**：GT1（局部智能指针）、GT2（成员指针）、GT3（宏展开取指针）三对全部通过——应用真实修复后检测必须"命中→消失、零误伤"。

**种子化召回基准**：开发集正向种子 11 个（覆盖 GT 形态、P6 双形态、P7/P8 双形态、P4/P5/P1）+ 负向种子 5 个（守卫/逃逸分支/free-置空等），独立文件归属，负种子声明须静默的模式族。实测召回 11/11、violations=0。该基准曾存在正负种子同文件导致误归属的问题，经外部复审指出后重写。

**P8 分支/闭包敏感化**：对异步回调型代码的两类系统性误报实现带因抑制。dsoftbus 实测中旧启发式产出 448 条候选，加入分支互斥 free 与回调闭包抑制后降至 69 条，移除的 379 条经抽查确认为错误分支路径或闭包生命周期差异所致。

**外部独立复审响应**：一份对最近 20 个 PR 的差异复审（含 32 项隔离实验）指出八项问题，全部经对照真实代码逐条复现并修复。修复内容包括种子基准归属重写、P6 守卫确认收窄、P8 抑制收窄、裸解引用等价形态、验证器状态拆分、影响矩阵证据分层。全部反例入回归测试。

#### 3.2.4 1-day 缺口与影响矩阵

向漏洞奖励计划提交 15 张已公开 CVE 的下游缺口工单（curl×2、openssl×1、ffmpeg×12），全部附 PoC/patch/验证记录，当前评审中。

20 案 × 6 分支影响矩阵全部录入判定，其中证据层级分为三类：第三方组件经分支钉版联接判定（manifest 钉版 → README 版本实证 → kb 受影响区间），OH 原生组件经符号级探测判定（漏洞函数逐分支存在性），master 列以源码三侧对照为据。证据层级在矩阵图例中标注——钉版联接和符号探测弱于检出/复现级实证。

#### 3.2.5 证据质量

对 20 案 × 12 字段做出口级证据质量审计（工具化、可重跑）：PoC 与补丁字段 20/20 全覆盖，实质率从初始 54% 提升至 68%。

### 3.3 分析

系统在 68 万行真实代码库上验证了从检测到报告的全链路。检测质量的核心保障不是单一指标，而是三层独立评估的交叉：回放度量已知形态的覆盖、种子度量开发集上的召回与特异性、外部复审暴露盲点。误报治理的关键不是"阈值调优"而是"每个不发射的访问都有记录的原因"——这使误报治理成为可审计的语义论证。

真库验证的价值在于将"发现"与"可评审证据"分离：隔离环境中的崩溃信号不等同于产品漏洞确认，但 gdb 帧归因到库内源码行 + 对照组合法返回 + 双 ASLR 一致性，构成了提交漏洞奖励计划所需的最低证据标准。证伪同样有价值——它关闭候选的产品影响主张，避免无效工单浪费评审资源。

## 第四章 创新性说明

### 4.1 语义分层的检测管线

本作品的核心检测创新是指针状态模型：对每个指针变量建立 Null/NonNull/MaybeNull 三态时间线（赋值、判空、解引用事件序列），检测输出不是"疑似告警"而是分层的可证明性结论。每个不发射的访问在抑制日志中记录原因，使 68 万行代码上 2,662 条候选到 13 条高价值线索的收敛过程完全可审计——误报治理从"阈值调多少"转变为"状态机论证是否成立"。

在通用检测之外，从仓颉 FFI 的 ABI 结构体契约推导出三类特有模式族，将此前未被自动化工具覆盖的跨语言调用边界纳入检测范围。

### 4.2 真库验证阶梯与确定性判读

将"发现"与"可评审证据"分级的四级验证阶梯：官方完整树零源码改动构建、对照矩阵运行、双 ASLR gdb 帧归因、结论与归档。配套两项确定性判读技术：分配器填充差分（同一畸形输入在两种填充字节下输出帧校验和不同，证明未初始化堆字节流出）和 ASan 分配上限定点拦截（报告直接指向无界分配行）。

UDMF 案的 round-trip 论据（getter 合法输出回喂 setter 必崩）将可达性论证从"存在恶意调用者"提升到"正常 API 使用模式即触发"。

### 4.3 检测质量的可测量化

漏洞挖掘工具通常只报告产出、不度量自身。本作品建立了三层检测质量评估协议：严格修复对（应用真实修复后检测必须命中→消失）、种子化召回基准（正向负向分离、独立文件归属、反向测试锁定）、外部独立复审（八项发现全部修复并入回归）。检测器自身的可信度因此成为可测量、可外部检验的对象。

### 4.4 LLM 的受控集成

生成侧：四步闭环（状态模型语义注入 → 编译反馈环 → ASan 执行 → 真库 dlopen 验证）。治理侧：LLM 永不产生漏洞结论（强制 undetermined 出口）、路径包含与注入防御、危险 API 输出屏蔽、密钥仅运行时环境变量。26 组审查队列全部执行完毕，26/26 草稿 final_verdict 均为 undetermined——纪律在规模下不变形。

### 4.5 证据工程

20 案证据链含五段式结构（源码位置/CWE/触发条件/PoC/影响评估），三出口一致性由契约测试锁定（工作台/矩阵/报告同输入同判定），证据质量成为可回归的工程属性而非一次性人工承诺。分支影响矩阵对 20 案 × 6 分支全部录入判定并区分证据层级。

## 第五章 总结

本作品实现了满足赛题六项能力要求的自动化漏洞挖掘与验证系统。核心成果：

- **检测**：13 模式族覆盖七类漏洞，在 68 万行代码上产出 2,662 条候选经语义收敛至 13 条高价值线索，误报治理精确消除 229 条宏守卫误报；
- **验证**：6 个高价值目标中 4 项获得运行级 SIGSEGV 证据（2 项已提交漏洞奖励计划、2 项材料齐备待提交）、2 项经运行排除并如实归档；
- **缺口判定**：15 张已公开 CVE 的下游缺口工单已提交，合计 17 单评审中；
- **影响评估**：20 案 × 6 分支全部录入判定，证据分层标注；
- **质量保证**：三层独立评估（严格修复对、种子化基准、外部复审）加 1,191 项回归测试。

**适用范围**：真库级验证在隔离自定义配置下完成，产品环境可达性为后续独立验证。访问识别为词法层，AST 级识别为后续演进方向。影响矩阵中钉版联接和符号探测类格子的证据强度弱于检出/复现级实证。cfhd 案需上游系数样本、nvdec 需 GPU 环境、curl 案需特定 TLS 后端，均如实标注验证边界。

**后续方向**：结构感知的边界模糊测试、AST 级访问识别、产品级可达性验证。
