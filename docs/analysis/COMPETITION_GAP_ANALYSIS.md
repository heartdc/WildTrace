# WildTrace 与 OpenHarmony 漏洞挖掘赛题差距分析

## 1. 结论

WildTrace 已形成防御性本地代码审计 MVP，并完成 Phase 4 的静态证据复核闭环、Phase 5 的部分报告链路和 Phase 6 的性能评测原型。距离比赛要求的完整自动化漏洞分析工具仍有明显差距，最大短板是语义分析、真实固定版本与分支影响、补丁有效性、规模化性能、完整交付材料，以及比赛 PoC 要求与项目安全边界之间的冲突。

比赛要求可执行 PoC；项目安全边界禁止真实攻击载荷、真实目标执行和自动确认漏洞。因此当前只能提供合成输入、证据复核程序和 review-only harness。主机测试不能表述为 OpenHarmony 漏洞确认。

## 2. 比赛要求基线

比赛要求工具具备：

1. 大规模自动化分析 OpenHarmony 源码。
2. 识别缓冲区溢出、空指针、整数溢出、UAF、信息泄露、权限提升、逻辑漏洞等类型。
3. 输出 CWE、已有 CVE、触发条件和漏洞详情。
4. 评估严重程度、代码模块、功能模块和版本分支影响。
5. 提供修复建议或补丁方案。
6. 生成包含源码位置、漏洞详情、PoC、影响分析和修复建议的报告。
7. 提供源码、技术说明、使用说明、Demo、漏洞分析报告和性能说明。

评价还包括准确性、完整性、CVE/CWE 准确性、PoC 质量、分支影响、修复建议、性能、创新性、覆盖率和易用性。

## 3. 当前能力

### 已具备

- 本地 C/C++ 静态规则扫描和行级证据哈希。
- EvidenceBundle、CWE 候选、人工忽略和规则基准。
- 本地漏洞元数据匹配原型。
- 报告、审核、归档、检查点、恢复和重试预算。
- 源码快照、路径隔离、符号链接边界和覆盖保护。
- 分片清单、分片扫描、分片合并和资源上限。
- 本地行哈希独立复核和合成 review-only harness。
- checkpoint/result/harness 联合校验和 `local_verification` 门控。
- 分支影响比较、补丁路径范围和文件 SHA-256 校验。
- 影响报告、审核批次、性能基准、性能矩阵和退化比较。
- 可选 LLM 草稿适配器、离线 CI、凭据扫描、打包入口和演示流程。

### 证据限制

已有 Windows 和 Ubuntu 离线测试；timer_task 样本曾完成 29 条候选的行哈希复核；性能基准只使用合成 C 源码。这些证据证明工程门控可运行，不证明真实漏洞、真实平台影响或比赛评分达标。

## 4. 差距矩阵

| 比赛要求  | 当前实现                | 主要差距                       | 风险  | 建议目标               |
| ----- | ------------------- | -------------------------- | --- | ------------------ |
| 大规模分析 | 受控分片调度              | 尚未完整仓库长期运行，缺取消、超时、峰值内存和覆盖率 | 高   | 真实固定版本分片评测         |
| 多漏洞类型 | 少量启发式规则             | 未覆盖 UAF、权限、信息泄露和逻辑漏洞语义     | 高   | AST/CFG/DFG 与跨函数分析 |
| CWE   | 规则映射候选              | 缺少上下文和人工标注支撑               | 高   | 分层标注集与证据绑定         |
| CVE   | 本地元数据匹配             | 缺固定来源、版本和可信绑定              | 高   | 版本化本地数据库           |
| PoC   | 合成 harness          | 不满足无条件真实可执行 PoC            | 高   | 明确授权的隔离验证环境        |
| 分支影响  | JSON evidence_id 比较 | 缺真实提交区间和版本映射               | 高   | Git adapter 与影响图   |
| 补丁验证  | 路径和 SHA-256 校验      | 未证明补丁消除真实候选                | 高   | 补丁前后独立复核           |
| 报告    | 候选报告和审核批次           | 缺指定版本完整漏洞报告                | 高   | 固定版本报告模板           |
| 性能    | 合成耗时、吞吐和退化          | 缺完整源码数据和内存报告               | 高   | 固定环境性能实验           |
| 易用性   | CLI、打包、Demo 文档      | 缺最终视频和故障说明                 | 中   | 干净环境演示包            |
| 创新性   | FSM、证据链、受限 Agent    | 缺完整对比和消融实验                 | 中   | 技术说明和对比实验          |

## 5. 架构差距

### FSM 和检查点

需要把验证记录正式写入检查点主链，统一报告、审核、归档和性能结果的迁移门控，并完善取消、超时、恢复和重试预算的端到端保持。

### Agent 和 LLM

需要固定输入输出 schema、证据引用、模型和提示版本记录，并保证 LLM 只能提出候选、解释证据和列出复核问题，不能确认漏洞或生成真实载荷。

### Domain

需要统一规则命中、人工抑制、候选审核、独立复核、harness、分支影响、补丁、性能和最终人工确认的生命周期，区分候选、可复现证据、人工接受和漏洞确认。

### Adapter

仍缺固定版本 Git、AST/CFG/DFG、隔离构建、资源采集和多文件事务持久化适配器。

## 6. 安全边界冲突

比赛要求 PoC 具有可执行性、稳定性和复现性；项目边界禁止真实攻击载荷、真实目标执行、自动报告和 LLM 独立确认。可接受策略是对合成输入提供可执行 harness，对真实源码提供静态复核和人工审核草稿。若比赛把真实可执行 PoC 作为硬性条件，这是当前明确差距，需要负责人另行做授权与隔离环境决策。

## 7. 实施路线

### Phase 5 收尾

1. 固定版本和提交区间的本地 Git 输入契约。
2. 绑定提交、文件、扫描结果和补丁摘要。
3. 统一补丁前后扫描、独立复核、报告和审核批次。
4. 生成指定版本候选漏洞报告。
5. 联合校验报告、审核、归档、检查点和 link。

### Phase 6 交付

1. 运行多规模分片性能矩阵。
2. 记录耗时、峰值内存、吞吐、失败分片和覆盖范围。
3. 固定环境、源码版本和基准参数。
4. 完成安装、扫描、验证、影响比较、联合验证和性能演示。
5. 完成技术说明书、用户手册和 Demo 材料。
6. 做最终仓库安全和凭据审计。

## 8. 最终验收

- 指定版本或提交范围可以重放。
- 扫描可分片、可恢复、可取消且有资源上限。
- 每条候选都有位置、行哈希和证据引用。
- CWE/CVE 来源、版本和摘要明确绑定。
- 分支影响有提交级证据。
- 补丁前后可比较并有独立复核记录。
- 报告、审核、归档和检查点联合一致。
- 性能数据来自固定环境和可重复实验。
- Demo 可在干净环境运行。
- 仓库和 CI 不包含 secrets。
- 候选和主机测试不会被描述为已确认漏洞或平台结论。

## 9. 当前判断

WildTrace 适合作为比赛原型基础，但尚未满足比赛全部要求。优先完成固定版本、提交区间和补丁证据闭环，再完成规模化性能和交付材料；在此之前不要宣称比赛要求已全部满足。

## 10. 人力与自动化分工建议

这张差距矩阵不仅用于描述缺口，也应作为项目资源分配依据。确定性、重复性和格式化工作适合自动化；需要安全判断、版本语义和业务上下文的工作应由人主导或最终批准。

| 比赛要求 | 更适合人力完成的部分 | 适合自动化的部分 | 责任主体 |
|---|---|---|---|
| 大规模分析 | 选择版本、提交区间、目录范围和排除策略 | 分片调度、遍历、恢复、合并、资源统计 | 人机协作 |
| 多漏洞类型 | 判断真实安全影响、调用链和业务语义 | 危险 API、内存模式和权限检查初筛 | 人机协作 |
| CWE | 结合上下文确认最终 CWE | 生成 CWE 候选和理由 | 人工主导 |
| CVE | 核对真实对应关系、版本和修复提交 | 固定本地数据库检索和候选匹配 | 人工主导 |
| PoC | 设计触发条件、验证边界和隔离方式 | 合成输入、harness 重复运行和记录 | 人工批准 |
| 分支影响 | 判断跨分支和组件的实际影响 | 提交、文件、摘要和差异计算 | 人机协作 |
| 补丁验证 | 判断是否解决根因和引入新问题 | 补丁前后扫描、摘要校验和差异输出 | 人工主导 |
| 报告 | 漏洞本质、风险、影响和修复说明终审 | 证据、结果和审核记录格式化 | 人工终审 |
| 性能 | 设计基准、解释异常和判断代表性 | 计时、吞吐、峰值资源和失败统计 | 人机协作 |
| 易用性 | 设计流程、提示和演示叙事 | CLI、参数校验、日志和导出 | 人机协作 |
| 创新性 | 定义方法、假设、取舍和实验 | 对比数据、消融实验和可视化 | 人工主导 |

### 10.1 适合机器独立完成的工作

机器应独立完成文件遍历、路径校验、哈希计算、规则匹配、结果合并、schema 校验、资源统计、报告格式化和 CI 回归。这些任务规则明确、重复性高，适合确定性实现。

### 10.2 适合机器提出、人确认的工作

漏洞类型、CWE、CVE、分支影响、修复建议、影响路径和 LLM 解释可以由工具生成候选，但必须保留证据引用、理由和人工审核状态。

### 10.3 应由人主导的工作

人应主导比赛范围选择、真实漏洞判断、普通 bug 与安全问题区分、DoS 安全价值判断、CWE/CVE 最终确认、补丁根因判断、跨分支影响解释、PoC 授权决策和最终报告定稿。

### 10.4 必须人工批准的操作

对真实 OpenHarmony 代码进行构建或运行验证、执行可能触发内存错误的测试、评估权限和信息泄露影响、生成真实输入、发送漏洞报告或把候选升级为确认漏洞，都必须经过人工批准。FSM 负责设置门控，工具负责准备材料和记录结果。

### 10.5 推荐协作流程

```text
工具扫描
  → 生成候选和证据
  → LLM 解释候选并提出复核问题
  → 人工确认漏洞类型和影响
  → 工具生成报告和补丁验证草稿
  → 人工批准验证
  → 工具记录结果
  → 人工终审报告
```

建议在原差距矩阵中增加“责任主体”列，使用“自动化”“人机协作”“人工主导”“人工批准”四类标签。这样矩阵可以直接指导开发排期、审核流程和比赛交付分工。

## 11. 更新后的当前判断

WildTrace 的自动化骨架已经足以支撑候选扫描、证据整理、分片处理和性能原型；真正决定比赛结果的工作仍集中在人力密集的范围选择、候选确认、版本影响、补丁判断、报告定稿和安全验证授权。后续应优先把工具做成可靠的证据准备系统，再由具备 OpenHarmony 经验的人员完成高判断密度环节。

## 12. 面向比赛的复用优先规划

### 12.1 总体取舍

项目不自研通用 Agent、C/C++ 解析器或通用数据流分析器。比赛得分更直接取决于漏洞覆盖、准确性、证据质量、补丁影响、性能和交付完整度。WildTrace 的独特职责是把成熟分析引擎组织成可审计、可复现、受人工控制的 OpenHarmony 分析流程。

### 12.2 推荐架构

```text
固定版本本地源码
        → 本地 Git / 输入校验
        → 成熟分析引擎适配器（Clang、CodeQL、Semgrep 等）
        → 统一候选与证据模型
        → 本地 CVE/CWE 知识库、确定性去重与排序
        → 受限 LLM 草稿解释
        → FSM 门控
        → 隔离验证、补丁前后复核、人工审核
```

FSM 继续负责状态、门控、重试、超时、证据一致性和人工审核。LLM 只处理结构化候选的解释、归并和审核草稿，不得改变状态、执行目标代码或确认漏洞。

### 12.3 自研与复用边界

| 能力 | 规划 | 说明 |
|---|---|---|
| FSM、状态门控、证据链 | 自研并保持核心 | 这是可信性和可复现性的基础 |
| C/C++ 解析、CFG/DFG | 复用成熟工具 | 优先接入 Clang、CodeQL、Joern 或编译器分析能力 |
| OpenHarmony 特定规则 | 少量自研 | 聚焦 API、组件和平台语义 |
| CVE/CWE 知识库 | 自研本地版本化层 | 保留来源、版本、摘要和哈希绑定 |
| 通用 Agent 框架 | 不自研 | 复杂度高、比赛直接收益有限 |
| 受限 LLM runner | 实现最小适配层 | 仅允许结构化输入、草稿输出和 FSM 进入人工审核 |
| 最终漏洞确认 | 人工结合确定性证据 | 候选不得自动升级为确认结论 |

### 12.4 实施顺序

1. 建立 Clang/CodeQL/Semgrep 等引擎的统一适配器和结果转换层。
2. 先实现一到两个高价值语义漏洞族，并建立人工标注的本地基准集。
3. 将本地知识库接入扫描流程，用于已知 CVE/CWE 候选召回和交叉验证。
4. 在核心分析稳定后实现最小受限 Agent runner，记录模型、提示词版本和输入输出摘要。
5. 完成固定版本大规模运行、补丁前后复核、性能实验、报告和演示材料。

### 12.5 受限 Agent 的必要性判断

完整 Agent 框架不是比赛必需项；最小受限 Agent 适配层有辅助价值，但优先级低于语义分析能力。它可以汇总多个引擎候选、解释调用链、建议 CWE/CVE 映射、生成审核草稿和提出人工复核问题；不得自主选择任意工具或路径、执行目标程序、生成真实攻击载荷、修改外部仓库或宣布漏洞成立。

该规划不改变当前安全边界：所有结果仍是候选，主机或合成测试不能直接代表 OpenHarmony 平台结论。

## 13. 审查后的执行顺序

代码审查显示，当前治理和证据链已经领先于核心分析能力。因此后续不再优先堆叠外围功能，按以下顺序推进：

1. 修复适配层正确性：分片 `alert_id` 唯一性、引擎来源区分、外部结果完整校验、分片直接路径读取和快照一致性。
2. 固定一个依赖闭合的 OpenHarmony 组件 profile，记录 commit、include、define 和编译参数。
3. 在该组件上完成 Clang Analyzer 与 clang-tidy 的多文件统一分析。
4. 只选择一个跨函数工具做小规模对比，不同时引入多个新引擎。
5. 优先扩展 UAF/生命周期和权限/IPC 两个漏洞族。
6. 再进行补丁前后复核、人工标注和真实性能评测。
7. 最后完成受限 Agent、报告、演示和交付材料。

GLM-5.3 可以编辑测试、规则草稿、评测脚本和文档，并通过独立 PR 参与；FSM、证据模型、结果校验和主事务链由 Codex 维护，最终安全判断由用户批准。

### 13.1 跨函数工具试验记录

已在隔离合成 C 样本上用 Semgrep taint 规则验证 `getenv` → `strcpy` 数据流捕获成功。规则保存在 `docs/design/semgrep_taint_pilot.yml`；这只是工具能力试验，不是 OpenHarmony 漏洞结论。下一步应在完整组件 profile 上运行并转换为统一 EvidenceBundle。

## 14. 最新代码审查结论

### 14.1 方向判断

总体架构没有跑偏，但工程治理、证据链和引擎接入已经领先于核心语义分析。后续不再优先增加外围模块，转向真实组件构建上下文、跨函数分析和高价值漏洞族。

### 14.2 已确认的核心边界

- 内置 scanner 仍是逐行正则，适合初筛，不能承担完整语义分析。
- Clang/clang-tidy/Semgrep 已能在 cameraApp 组件范围运行，但 profile 仍主要由 GN 配置手工提取，尚未等价于完整 GN/Ninja 编译数据库。
- function-scope 规则适合作为实验分支和误报研究，不应当作 AST/CFG 分析器。
- triage 设计稿暂不进入 FSM 主链。
- 知识库同步解决已知漏洞召回，不解决新漏洞发现。

### 14.3 新执行顺序

1. 收敛适配器正确性和结果校验。
2. 固定 cameraApp 的真实编译 profile，并尽量生成 GN/Ninja 编译命令对照。
3. 只选择一个跨函数工具做小规模比较。
4. 优先完成 UAF/生命周期语义，再做权限/IPC 边界。
5. 完成补丁前后比较，再恢复人工标注和真实性能评测。

### 14.4 暂缓事项

暂缓通用 Agent、triage FSM 实现、大量简单正则、多个新引擎同时接入以及大规模准确率宣传。所有合成 benchmark 仅用于规则回归，不外推为 OpenHarmony 平台指标。
