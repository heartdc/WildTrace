## 结论与范围

WildTrace 已有可用的静态分析、编译器事实、知识库、证据校验和案例验证基础，但尚不能作为完整比赛交付验收。优先级应从扩充通用框架转向：降低误报、证明真实安全影响、打通指定版本的完整案例、补齐五项交付物。

依据：本仓库 `doc_text.txt` 的赛题原文；当前 HEAD `ed32631` 加现存未提交改动。检查了扫描器、FFI 专项、triage、报告、影响比较、性能、基准评测、编译器入口、案例和交付文档。执行离线单元测试及临时合成输入反例；没有重新运行目标 PoC、联网验证 CVE/工单或调用模型。不是逐行穷尽审计，历史运行结论仍须核验原始证据。

## 已复现的代码问题

### P1：每个分片重复无界整树快照，缺失文件也先扫描全树

位置：`ohvul/source_snapshot.py:4-10`；`ohvul/engine_shards.py:23,68,96-106`。

全量回归中的 `test_engine_shards.EngineShardTests.test_missing_file_is_input_error` 使用当前项目根目录。首次执行长时间未完成，Python 工作集超过 2 GB，停止后以 faulthandler 诊断重跑，再次停在 `source_snapshot → sorted(root.rglob('*'))`。60 秒堆栈已保存在 `.cache/competition-audit-20260923-diagnostic-tests.log`。这是当前带缓存工作区的实测阻塞，不能据此断言干净 CI 同样失败。

代码在验证具体文件存在之前先遍历整树；快照枚举所有目录，再读入每个文件的全部字节，没有区分目标输入、缓存和 Git 元数据。manifest 前后和每个 shard 前后重复整树快照，S 个分片会产生约 2S+2 次整树快照。单个引擎 timeout 不约束这一步。

比赛影响：全树/大仓库性能瓶颈、额外内存开销、输入错误反馈极慢；仓内输出或日志变化还可能改变快照。现有合成性能工具未覆盖此路径。

修复验收：先验证清单；定义包含实际源码及依赖的输入集合，对非输入目录做明确范围区分；流式哈希并加入时间/文件数/字节预算；在批次内复用清单与摘要，仍保留必要的执行后变更校验，不能简单删除来源保护。测试改用隔离临时目录并加入“单文件请求不扫描无关缓存”“分片不重复全树工作”的资源/调用次数回归。

### P1：FFI 扫描失败仍返回成功，覆盖率不可信

位置：`ohvul/ffi_boundary_audit.py:74-100,147-166`。

最小反例：目录只含非法 UTF-8 的 bad.cpp。CLI 输出 `candidates=0 files=0`、退出码 0，JSON 含 1 条 input_errors，却没有整体失败状态。显式输入不存在的 missing.cpp 则得到 `files_scanned=1`、空错误列表。

原因：跳过文件没有独立计数，files_scanned 用请求数减错误数推算；main 无条件返回 0；os.walk 没有 onerror，枚举失败也可能静默丢失。

比赛影响：会把分析失败展示为零候选，把未读文件算作覆盖，损害完整性与性能数据可信度。

修复验收：复用主扫描器逐文件记录与 completed/partial/input_error 契约；只统计成功读取解析的文件；失败退出非零；枚举失败标 scope_complete=false。增加全失败、部分失败、缺失文件、枚举异常反例。

### P1：FFI 注释误报与 CWE 过度分类

位置：`ohvul/ffi_boundary_audit.py:107-145`。

实测纯注释 `// struct Fake { int *head; int size; };` 加 `// use(a.head[0]);` 产生 1 条 CWE-125 候选。写语句 `a.head[0] = 1` 也统一标 CWE-125（越界读），没有区分读写，更没有证明越界。

原因：直接对未遮蔽注释/字符串的全文做正则匹配；跨文件关联只看 head/data 等字段名，未绑定对象真实类型；CWE 固定为 125。

比赛影响：准确率和 CWE 分类均可能扣分；“候选”标签不能替代质量治理。

修复验收：复用已有词法遮蔽、保持原始行号；无类型证据时仅作导航线索；区分空指针、越界读、越界写，证据不足保留 unknown。加入注释、字符串、同名异型对象、合法访问、写访问和守卫正反例。不要用附近 600 字符出现 NULL 作为安全证明。

### P1：显式文件列表可越过声明源码根目录

位置：`ohvul/ffi_boundary_audit.py:86-90`。

实测 `audit_source(root, ['../outside.cpp'])` 成功读取根外临时文件，并输出位置 `../outside.cpp`。当前 CLI 不暴露此参数，影响范围是 Python API 及将来的批处理接入；不是已证明的远程攻击入口。

修复验收：复用 source_scope 的规范相对路径和根目录边界校验，拒绝父目录、绝对路径、链接及重复别名；在读取前完成校验。

### P2：候选评测不能直接当比赛漏洞准确率

2026-09-25 后续修复：保留旧聚合入口并明确 `metric_scope=file_cwe_presence`；新增 `evaluate_location` 和 CLI `--location-metrics`，按快照绑定的位置标注进行最大一对一匹配，额外重复告警计 FP。复核声明、快照、执行状态或标注不完整时输出 `not_evaluable` 且无指标数字；严格 CLI 返回退出码 2。失败文件精确路径关联及资源上限已加入。相关新增/兼容测试共 33 项通过。现有合成文件级标签没有升级为人工真值；冻结真实位置标注、根因级指标和重复率仍未完成。

位置：`ohvul/engine_benchmark.py:evaluate`。

旧入口按“文件/案例 + CWE 集合”计数，不匹配缺陷位置和根因。审计反例中同一文件放入 50 条同 CWE 告警，只计算 TP=1、FP=0、precision=1.0；这不是 50 条告警都正确的证明。新增严格入口的合成回归已确认对应结果为 TP=1、FP=49，比赛材料还需要真实人工标签支撑。

修复验收：分别报告告警级 precision、根因去重后的漏洞级 precision/recall、重复告警率、未知率及分析失败率；用人工标注位置/根因匹配。训练开发样本与冻结评测样本分离，不将复现已知案例的回归集包装成发现能力。

## 下一步执行顺序

以下是工作顺序和验收目标，不是已确认截止日期下的工期承诺。

### P0：先阻断比赛扣分与交付失真

1. 先修复整树快照的重复遍历与无界资源使用，再修复 FFI 失败语义、误报/CWE 与路径边界，接入主结果契约及离线 verify。新增模块应复用已有正确实现。
2. 建立单一案例台账：每例区分候选、源码核验、等价 harness、真实库复现、产品影响、已提交、官方接受；分别记录，允许未知。把人工发现、已知漏洞回验和自动检出分开。

4. 给 IPC/KV 设止损门槛：先追踪支持的调用入口和权限边界。若只能由本进程构造非法裸指针导致自身崩溃，且无额外安全影响，降为健壮性问题，不挤占主报告名额。先查源级调用链和构建包含关系，再决定是否投入完整产品构建。
5. 将当前有效新增代码、测试和材料纳入唯一交付版本；将外置附件整理为可迁移且带摘要的私有交付包，避免依赖 D: 和 .cache 的绝对路径。提交工单后按真实回执更新，官方评审仍单列。

### P1：用一个纵向闭环补齐硬交付

6. 冻结一个主比赛目标版本/manifest与构建配置，同时保留多组件总范围；优先把一个高价值案例完整串起来。闭环是：固定源码 → 自动发现/检索 → 复核 → 可执行 PoC → 安全影响 → 修复对照 → 分支矩阵 → 报告。
7. 实现比赛报告组装器和交付包完整性检查；不要把当前 candidate-only 报告的 confirmed 数字硬改为正数。人工结论和运行证据应独立引用。
8. 固定真实源码范围做性能测试，明确全树可读文件、成功编译单元、词法分析文件、失败/跳过的不同分母。3,901 个文件的词法扫描不等于完整 OH 产品构建覆盖。
9. 完成环境预检、正式使用手册、真实案例演示脚本、录屏与技术说明书 v1.0。让另一位成员在干净环境独立执行并记录失败原因。

### P2：有可交付基线后再争取增量分

10. 用冻结的独立标注集做误报和消融；有证据再宣传效率/准确率提升。
11. 将现有人工案例反哺自研检测；选择 1–2 类能验证输入来源与权限边界的缺陷，避免扩充低价值空指针告警数量。
12. LLM 全量评审和双模型实验是可选提效/创新验证，不应成为正式报告、真实性能和案例闭环的前置条件；模型分歧清单供人工处理。

建议投入比例：约 50% 案例安全影响与复现闭环、25% 误报与结果集成、25% 性能和交付材料。此比例为规划建议，不是赛事评分权重。近期暂缓新引擎、通用 Agent 框架和更多归档层，除非直接解决闭环阻塞。

## 最低交付验收线

- 一份固定版本/范围清单；一套可安装且预检通过的工具源代码。
- 至少一条真实源码、真实构建/组件和安全影响有据的完整案例闭环作为内部最低目标；不是声称赛题只要求一例。其余发现逐例达到相同报告字段完整度。

- 五项交付齐全：源代码、技术说明书、使用手册+视频、指定范围漏洞报告、真实性能说明。
- 干净环境独立复跑，完整测试通过；已提交、官方接受、新发现数量各有独立口径。
- 截止日期、官方指定版本/时间段和交付格式仍需按赛事通知确认；仓库设计稿中的日期不作为已核实官方期限。
