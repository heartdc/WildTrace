# 基线对比实验：版本匹配型扫描器 vs 三层管线 — 2026-09-28

面向技术说明书"创新性"节的实测数据：在同一棵 OpenHarmony 检出上，量化
"纯版本号匹配"与本项目三层管线（版本命中 → 树内指纹核验 → 产品配置可达性）
的产出差异。

## 方法

- **同一输入**：完整 OH 检出（`C:/Projects/OpenHarmony`，182 个 third_party 组件），
  组件名与版本全部取自 `README.OpenSource`（JSON 清单解析，#41）——三列方法共用，
  输入公平。
- **基线列 1（OSV 通道）**：对每个组件以 `pkg:generic/<name>@<version>` 查询
  `api.osv.dev/v1/query`（2026-09-28 实测；OSV-Scanner 对 SBOM/无锁文件源码树
  走的就是该通道）。命名敏感性已测：`curl`/`libcurl` 两种拼法均 0 命中。
- **基线列 2（CVE 列表版本匹配，CPE 语义）**：本项目 `kb_version_probe` 的第一层
  （exact 命中）——与 CPE 型扫描器（Trivy 等）同范式，数据源 cvelistV5。
- **本项目列**：三层全管线；第二层（树内指纹）与第三层（产品配置可达性）的
  curl 结论依据 `CURL_MIDDLEFORM_VERIFY_20260921.md`（PR #42）及其复核。

## 结果

| 方法 | 产出（同一棵树，182 组件） |
|---|---|
| OSV API 版本匹配（generic purl） | **0 条 CVE**；4 个组件共 6 条 OSS-Fuzz 号（HarfBuzz、libbpf、libxml2、PCRE2） |
| CVE 列表版本匹配（exact 命中层） | **47 条 CVE**（curl 43、libxml2 3、libpng 1） |
| + 第二层：树内指纹核验 | curl 43 → **2**（41 条已被 OH 快照升级/显式回移修复，版本号未反映） |
| + 第三层：产品配置可达性 | 2 → **0**（libpsl 未启用 / native CA 仅 Win+macOS，见 #42） |

## 读数

1. **两个方向都错，且错法相反**：OSV 通道对 vendored C 组件严重欠报（curl 8.8.0
   有数十条真实 CVE，返回 0——上游公告不在 generic 命名空间）；CPE 语义版本匹配
   则过报（47 条里 41 条在树内已修复——活跃同步组件上版本号是弱信号，#42 方法论
   发现的实测放大）。
2. **准确率来自后两层，不来自匹配层**：指纹核验消掉 95% 的 curl 版本命中
   （41/43），产品配置层把余下 2 条正确归零。替换掉这两层中的任何一层，结论都会
   从"0 条产品可达"变成"0 条"或"47 条"。
3. OSV 通道返回的 OSS-Fuzz 号是按提交区间的模糊匹配，不构成 CVE 主张；本实验
   未将其计入任何 CVE 口径。

## 边界与未覆盖项（如实）

- **Trivy 未测**：实验时段 github.com 不可达，二进制无法获取。其 DB 以 NVD/
  公告为主、按 CPE 模糊匹配，预期行为接近"列 2"，但这是推断不是实测——标注为
  未覆盖，日后网络恢复可补一列。
- OSV 查询为在线 API（无凭证），查询日期 2026-09-28；原始结果存
  `.cache/osv_full_results.json`（本地工件，不入库，数字已录入本文）。
- 版本串来自人工维护的 README.OpenSource——三列共用同一输入，公平但绝对精度
  受其限制（#41/#42 已论述）。
- 本对比是方法论层面的（版本匹配范式 vs 三层管线），不是产品级漏洞结论；
  全程确认漏洞数口径不变（0）。

## 去向

叙述，而是同一棵树上的对照实测。
