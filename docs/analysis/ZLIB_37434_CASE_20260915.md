## 为什么选择这个案例

这是一处已公开、已修复的 zlib gzip 头处理内存安全漏洞，而不是根据危险
API 名称猜出的缺陷。目标是先验证实际漏洞、修复和完整报告链；不宣称为
WildTrace 自动发现的新漏洞，不计入新发现或奖励计划认可数量。

上游说明：inflateGetHeader() 接收的 extra 缓冲区可以小于 gzip FEXTRA；
API 只应保存可容纳部分。旧代码跨多次 inflate() 处理头部时，缺少对已经
处理偏移的检查，可能对 extra_max - len 进行无符号下溢并越界复制。
适用前提包括调用 inflateGetHeader、提供 extra 缓冲区、扩展头较大以及分段
输入。仅依赖或打包 zlib 不能证明产品可达该路径；不宣称实际远程代码执行。

## 最小复现草稿与对照

草稿：tools/validation_cases/zlib_gzip_extra_37434.c。
不含网络、命令执行、任意输入或大块分配；固定一个有效的 gzip 数据流，
解压内容 WT-CASE\n；FEXTRA 长度 32，真实分配与 extra_max 均为 8。
先交付完整 12 字节头部及 12 字节扩展头，再交付剩余数据。按旧逻辑，第二次
处理时 len 为 12，大于容量 8，旧无符号差值会回绕。此推导不是运行证据。

四种模式：fragmented（目标情形）、whole（不分段）、no-capture（不启用
该 API 路径）、full-capacity（足额缓冲区）。成功模式必须同时验证解压原文、
流结束、输入消费、扩展头截取及 inflateEnd 返回值，不能只检验进程未崩溃。
草稿已通过针对本地当前 zlib.h 的语法检查；脆弱版本只应在获批隔离环境中用 AddressSanitizer
运行。不得以普通非零退出、超时、构建失败或测试自身错误计作触发。
