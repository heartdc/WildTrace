# 方案审查结论

## 1. 结论

现有 v2 方案可以作为工程总纲，优势是证据链、独立复现、确定性门控和报告字段较完整；但不宜直接按全文实现。应把“可参赛 MVP”收缩为一条稳定主链，再把高风险扩展作为可插拔能力。

## 2. 与赛题要求的对照

| 赛题要求             | 当前覆盖                       | 判断                           |
| ---------------- | -------------------------- | ---------------------------- |
| 自动分析 OpenHarmony | 仓库同步、commit 范围、三层静态        | 覆盖，但需先固定目标版本和组件清单            |
| CWE/CVE          | CWE 字段、OSV/NVD、补丁指纹        | 覆盖；CVE 匹配不能仅凭目录/版本，必须保留证据    |
| 可执行稳定 PoC        | 模板 + harness + ASan + 独立复现 | 方向正确，是方案最有竞争力的链路             |
| 影响范围/版本分支        | 函数指纹和分支矩阵                  | 可行，但要处理宏、重命名、回移植补丁           |
| 修复建议/补丁          | LLM diff + 回放验证            | 覆盖；必须区分“建议”和“已验证补丁”          |
| 报告               | 结构化报告和留痕报告                 | 覆盖                           |
| 性能               | 指标设计                       | 仅有指标，缺少固定基准、基线和验收阈值          |
| 多漏洞类型            | 首批偏内存安全/DoS                | 与赛题评分项存在冲突，需补至少一种信息泄露或权限边界规则 |

## 3. 必须修正的问题

### 3.1 “明确不做”与评分项冲突

赛题明确列出信息泄露、权限提升、逻辑漏洞等类型，并按类型多样性加权；方案把信息泄露、权限提升全部写入“不做”，会损失覆盖度。建议改为：首版不承诺全量支持，但至少实现一个低风险、可验证的规则，例如：

- 信息泄露：未初始化内存/越界读返回、敏感字段进入日志或 IPC 返回值；
- 权限边界：IPC 服务调用者权限检查缺失的候选发现和人工复核队列；
- 逻辑漏洞：仅做规则化、能给出明确前置条件的检查。

这些规则可以只做到 L1/L2，不必承诺自动提交，但要在报告中体现能力边界。

### 3.2 “主机验证即可提交”的表述必须收紧

方案允许 `host_verified` 进入待平台确认队列，并在风险表中写“按 host_verified 提交”。这容易与赛题要求的 OpenHarmony 代码漏洞报告和可复现性产生冲突，也可能形成未经平台确认的过度结论。建议明确：

- 主机验证只能标记为“候选/待平台确认”；
- 对外漏洞报告默认只提交 L3；
- L2 报告必须显式写“未完成 OH 环境验证”，不能写成已确认影响；
- 只有存在明确的环境不可用原因时，才把 L2 作为展示结果，不作为最终漏洞数。

### 3.3 动态门槛不能覆盖所有漏洞类型

“真实崩溃”适合内存破坏，但不适合信息泄露、权限绕过、逻辑缺陷。当前 triage 把执行证据和崩溃证据绑定过紧，可能漏掉非崩溃安全漏洞。应把判据抽象为“可观察安全效果”：ASan/UBSan 崩溃、敏感数据泄露、权限决策绕过、跨信任域未授权状态变化等，按 CWE 使用不同验证器。

### 3.4 决策表存在过度简化

“内存破坏类 + 可控性 >= len + 可达即报”会把不可利用或仅测试代码路径带入大量误报；`none` 也不等于一定是健壮性问题。增加最低约束：目标代码必须是发行构建可达路径、排除测试/示例/死代码、确认对象生命周期/边界条件和影响进程；把“可达”与“可利用”分开记录。

### 3.5 45 天计划过于乐观

W2 就提交第一批奖励计划、W3 达到 L3、W5 才开始 OH 复现，风险很高。建议把验收拆成硬 MVP：

1. 已知 CVE + 代码确认 + 报告；
2. 三类规则 + 一个稳定 PoC + 独立复现；
3. 分支影响和补丁回放；
4. 再扩展 CodeQL、双模型、OH 设备和 UI。

第一周必须完成一个端到端垂直切片，而不是只搭 LangGraph 和数据模型。

## 4. 应优先优化的工程点

- **工具可用性**：GPT-6/Grok、Docker、CodeQL、OH SDK 都应做能力探测和离线降级；不能把外部模型作为硬依赖。LLM 不可用时，规则扫描、CVE 匹配和报告仍应运行。
- **静态分析分层**：先实现 tree-sitter + compile_commands/Clang 两层；CodeQL 作为插件，不要进入主门禁。
- **去重与基准**：当前按“文件、函数、CWE”去重过粗，加入源码位置、调用链摘要、规范化缺陷签名和跨工具证据合并；定义 TP/FP/FN、PoC 成功率和 P95 耗时的固定数据集。
- **代码安全**：PoC、harness 和修复补丁都必须在专用沙箱中构建运行；禁止自动提交、自动联网扫描或自动向外部系统发信；报告生成器对未经人工审核的结果加状态标记。
- **证据模型**：EvidenceBundle 增加工具版本、规则版本、容器镜像 digest、输入生成器版本、时间源和权限配置；哈希链应有可校验命令。
- **模型实验**：论文中的 DeepSeek/ArkTS 结果不能直接外推到 C/C++ 和 OpenHarmony native 代码。应在本项目 C/C++ 基准上重新测量，不要把 95.24% 当作本项目指标。
- **OpenHarmony 兼容性**：主机 ASan 结果与 OH 运行结果要区分 ABI、编译器、宏和 IPC 序列化差异；host harness 应尽量调用真实组件入口，而非只复制函数逻辑。

## 5. 建议的参赛 MVP

目标只保留一条可演示主链：

`commit-range → 组件识别/CVE → tree-sitter 规则 → Clang 交叉确认 → triage → 2~3 个 PoC 模板 → 主机沙箱 → 独立复现 → 分支影响 → 报告`

首批优先：CWE-122/787、CWE-190、CWE-416；补一个信息泄露或 IPC 权限规则。每个漏洞至少产出源码位置、CWE/CVE、触发条件、可执行 PoC、两次独立复现、受影响分支和补丁回放结果。CodeQL、双模型交叉、OH 设备复现、Streamlit 放在 MVP 通过后的扩展层。

## 6. 参考论文的正确借鉴方式

两篇论文适合借鉴“指针/污点分析框架、插件化、LLM 生成转移规则、True/False 配对评测、缓存和失败回退”，不应直接把论文实验结果当成 OpenHarmony C/C++ 实际效果。ArkTS 应用污点分析与 native C/C++ 的内存安全、编译数据库和 ABI 问题不同，迁移必须用目标语言基准重新验证。

## 7. 推荐修改文档的具体位置

- §1.3：把“全部不做”改成“首版不承诺全量，至少提供一类信息泄露/权限边界候选规则”。
- §5：将“执行证据”改为“安全效果证据”，按 CWE 配置验证器。
- §7.3 和 §15：删除“按 host_verified 提交”的措辞，明确 L3 才是提交门槛。
- §12：增加固定基准、人工标注集、基线工具和目标阈值。
- §14：把 W1 改为端到端垂直切片，W2/W3 再扩展检测器和 PoC。
- §16：补充交付物检查清单、离线运行方式和已知限制。

## 8. 最终判断

方案有较强的参赛潜力，尤其是证据链、独立复现和 OpenHarmony 攻击面建模；当前主要风险不是“想法不够”，而是范围过宽、部分门槛定义不适用于非崩溃漏洞、时间表把多个高不确定性系统同时当成已可用。按上述 MVP 收缩并修正结论口径后，方案会更可信、更容易做出可展示结果，也更符合防御性代码审计定位。
